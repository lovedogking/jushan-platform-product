# 代码仓库 × 需求文档 V1.1 差距分析报告

> 分析对象：https://gitee.com/zeng-bohan-66/jushan-platform-product 分支 develop @ 5175a3b6（2026-07-17 拉取）
> 对照基线：《停车SaaS系统需求规格说明书 V1.1》（2026-07-16）
> 分析方式：全量代码扫描（557 个 Java 文件、75 个 Flyway 迁移、三端前端、关键特性逐一取证复核）

## 一、结论摘要

**相比旧版报告，大量地基已就位**：模拟支付全链路、远程开闸、Webhook 事件接收、月卡/固定车位管理界面、系统参数（全局）、岗亭监控面板、小程序缴费/代缴/余位/消息均已实现。

**但当前代码存在 3 个 P0 级问题，且 V1.1 收费闭环的关键机制仍然缺失**（出场窗口期、欠费链路、预订单状态机缺失；超时重计费虽有隐式行为但无幂等防重与留痕）。

## 二、P0 阻断级问题（必须先修）

### P0-1 `remaining_spaces` 列已 DROP、实体仍映射 🔴

迁移 `V20260724001` DROP 了 `parking_lot.remaining_spaces`（注释"改为区域汇总+Redis 实时计算"），后续仅 `V20260815002` 重建了 `current_vehicles`，`remaining_spaces` 未重建；而旧包 `ParkingLot` 实体仍映射该字段且无 `@TableField(exist=false)`。**全新数据库执行到该实体的查询/插入即报 Unknown column**。影响面比实体本身更大：`DashboardMapper` 有 `SUM(remaining_spaces)` 原生 SQL、`EntryService`/`ExitService` 有 `setSql("remaining_spaces ± 1")`——新库上驾驶舱查询与进出场链路都会炸。且"区域汇总+Redis 余位"的规划未落地（`ParkingSpacePolicyServiceImpl.calculateRemain` 中 `usedSpaces=0` 占位，TODO TASK-0601），余位实际靠 `current_vehicles` 推算——体系处于"拆了一半"状态。

### P0-2 设备 Webhook 无签名校验 🔴

`SecurityConfig` 第 57 行 `/api/v1/device-webhook/**` 全量 `permitAll`；`DeviceWebhookController/Service` 无 HMAC 签名验证（grep 0 命中）。存在可选 IP 白名单配置（`device-access.webhook.allowed-ips`，默认 `*` 等于全放行），但 IP 白名单不能替代防伪造签名。任何人可向平台伪造车牌识别事件、伪造开闸链路数据，直接违反 V1.1 SEC-005 与 COMM-002 的"签名校验防止伪造"。

### P0-3 设备唯一索引与 V1.1 双相机/双向通道硬性冲突 🔴

迁移 `V20260711010` 建了 `uq_lane_device_type (lane_id, device_type)` 唯一索引——**同一车道最多一台相机**。V1.1 ADMIN-004/005 要求：双相机主备模式（同车道两台相机）、双向通道须分别绑定入场/出场方向相机。当前 schema 在数据库层封死了这两种配置；且 `device` 实体无"识别方向""主备关系"字段。

## 五、架构级问题（影响后续所有开发）

1. **旧包冻结与现实的矛盾** 🔴：`com.jushan.system` 已包级 `@Deprecated`（只删不增），但它仍承载进出场、计费引擎、订单、模拟支付、设备、车场/车道、月卡/固定车位、系统参数、岗亭监控等约 80% 核心业务；新包 40+ 处反向 import 旧包。**V1.1 剩余缺口（收费闭环/月卡重建/名单/临牌）的绝大多数都长在这些旧包业务上**——"冻结旧包"与"完成 V1.1"在当前结构下互相打架，必须先做决策（见 D1）。
2. **五处双轨并存**：账号（`sys_admin_account` vs 旧 `sys_user`/employee）、公司（`sys_company` vs `company`，数据不互通）、计费规则（`fee_rule` 空转 vs `billing_rule` 在用）、车辆（`sys_vehicle` vs `vehicle`+`plate_binding`）、日志（`sys_business_log` vs `sys_audit_log`）。另有 `parking_lot`/`parking_lane` 同名实体新旧双映射同表。
3. **前端工程问题**：admin-web 存在 `/api` 双前缀 bug（fee-rule/fee-calculation 两模块请求 404）；菜单缺收费规则/费用试算/订单/黑白名单入口（只能直链）；`parking-lane`/`parking-zone` 逐字节重复的页面副本、`department` 孤儿模块、`HolidayRuleEditor` 已开发零引用。
4. **数据一致性隐患**：`sys_auth_code` 迁移建表但无任何代码引用（死表）；归档模块只有查询没有归档任务（空壳）。

## 六、需要你决策的 4 个问题

### D1 包结构收敛策略（最优先，决定所有任务包写法）
- **方案 A（推荐，务实）**：本期承认旧包为业务主战场，解除"只删不增"冻结为"受控使用"；新包保留已成型模块（auth/account/company/department、device-webhook、miniapp、parking-session/recognition-event）；新 fee_rule 计费体系代码已实现但未接入计费链路，本期标注冻结为二期候选（详见任务包 0-1）。V1.1 完成后（二期）再规划整体迁移。
  - 理由：剩余缺口 80% 在旧包业务链路上，强行迁移等于把 Phase1~3 已验证的功能重写一遍，风险大、周期长。
- 方案 B（理想，昂贵）：按旧版任务包 0-2/0-3 先完成订单/支付/计费整体迁移再开发新功能。预计多耗 1~2 周且有回归风险。
- **本报告配套提示词默认按方案 A 编写**；如选 B，阶段 0 需替换为迁移任务包。

### D2 范围蔓延功能处置
推荐：按第四节"建议处置"列执行（访客/钱包保留禁入口、岗亭扫码隐藏、超时拉黑加开关默认关、离线队列保留、真实支付脚手架统一 mock）。也可选择直接拆除。

### D3 小程序支付形态
推荐：本期小程序所有支付（自缴/代缴/月卡/固定车位）统一走模拟支付确认接口，摘除 `wx.requestPayment` 调用（代码保留注释三期）。

### D4 月卡重建方式
V1.1 要求独立月卡实体 + 审核流 + 缴费方式 + 月卡订单。推荐：新建 `monthly_pass` 表与实体（按旧版任务包 1-3 设计），现有 `MonthlyPassController` facade 与 `SysVehicle.vehicleType=MONTHLY` 模式废弃，存量数据 Flyway 订正。固定车位沿用 `fixed_space_binding` 扩展（补审核/缴费方式字段）。
