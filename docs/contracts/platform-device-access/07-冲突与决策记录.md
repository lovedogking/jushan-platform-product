## C01 [P0] 开闸接口存在性

- **来源文档**：`AGENTS.md §2.2`、`T01`、`docs/需求文档/停车业务平台与DeviceAccess接口规范.md`（第 1～18 章）vs `docs/ARCHITECTURE.md §5.2`、`CLAUDE.md`、Device Access v0.2 代码
- **冲突内容**：平台文档将 `POST /api/v1/devices/{deviceSn}/gate/open` 列为"当前真实接口"；Device Access v0.2 代码中该端点**从未存在**。
- **本轮代码核实（2026-07-11）**：
  - **DeviceController**（`device-access-api/.../api/DeviceController.java`）：7 个 HTTP 端点（校时、状态、设备 CRUD 5 个），**无 gate/open 映射**；
  - **DeviceService**（`device-access-api/.../api/DeviceService.java`）：`syncTime()`、`getStatus()`、设备 CRUD 方法，**无 openGate() 方法**；
  - **ZhenshiMessageHandler**（`device-access-adapter/.../adapter/zhenshi/ZhenshiMessageHandler.java`）：处理 `keep_alive`、`ivs_result`、`quick_ivs_result`；下行仅 `sendSyncTime()`（topic `device/{sn}/message/down/set_time`），**无 gate_direct_open Topic 或处理方法**；
  - **MqttGateway**（`device-access-mqtt/.../mqtt/MqttGateway.java`）：通用 `publish()`/`publishAndWait()`，**无开闸相关方法**；
  - `gate_direct_open` 字符串仅出现在注释中（`MqttMessage.java:41` Javadoc 示例、`MqttRequestPayload.java:17` Javadoc 示例），不是功能代码；
  - **Git 历史**：`b06daf4`（Device Access v0.2 首次 Java 代码提交，2026-07-11）中 DeviceController 即为 7 端点、无 gate/open。该仓库无更早的 v0.1 Java 代码提交。即 v0.2 代码从一开始就没有实现开闸接口。
- **AS-IS 分类**：**NOT_IMPLEMENTED_IN_V0.2**（当前未实现）/**INTENTIONALLY_OUT_OF_SCOPE_IN_V0.2**（v0.2 有意排除）。v0.1 文档描述了开闸接口，但 v0.2 代码创建时因 C5H 订阅列表不含 gate_direct_open 而有意不实现。不是功能回退（regression），是 v0.2 范围决策。
- **推荐 TO-BE**：目标版本以统一命令 `OPEN_GATE`（`POST /api/v1/commands`）重建开闸能力；C5H 实际开闸机制需真机确认（见 C11）。当前 Platform **不可**依赖开闸接口。
- **决策理由**：代码事实优先于平台文档（v0.1 描述已过期）。开闸是主链路必需，但必须基于真机确认的机制重建。C5H 的实际开闸机制（serial_data 下行？特定 Topic？RS485 继电器？）必须在真机上确认后才能实现。
- **影响系统**：Platform（开闸调用、AGENTS§2.2、T01 需更新）、Device Access（需从头实现开闸）。
- **是否需双方确认**：是（开闸机制与切换时点）。
- **是否阻塞最小真机闭环**：是（BLOCKING_FOR_MINIMUM_DEVICE_LOOP）。
- **最终状态**：事实 PROPOSED；开闸机制 NEEDS_DEVICE_VERIFICATION。

## C03 [P1] 响应成功码 code=200 vs code=0

- **来源文档**：`docs/接口规范/基础响应与认证契约.md`（R01 冻结，code=0，禁 code===200）vs Device Access `Result.java`（code=200）
- **冲突内容**：平台前端/内部契约成功码=0 且明确禁止 code===200；DA 成功码=200。两套不一致。
- **AS-IS**：DA `Result.ok()` 返回 code=200；平台前端 R01 返回 code=0（字段含 traceId/errors，DA 无）。
- **推荐 TO-BE**：建立**独立的服务间响应契约**——成功 HTTP 200/202 + `code=0`（业务成功）；失败用对应 HTTP + 6 位业务 errorCode（见 `05-target §13`）。既不沿用 DA 当前 code=200，也不照搬前端全部语义。Platform 前端 code=0 契约**仅适用于前端/内部接口**，不外推到服务间。
- **决策理由**：不得简单复制平台前端登录契约到 DA；服务间需稳定业务错误码而非 HTTP 状态混用。
- **影响系统**：双方（响应结构与错误码）。
- **需双方确认**：是。
- **最终状态**：NEEDS_HUMAN_DECISION（推荐如上）。

## C04 [P0] deviceId == 厂商 SN

- **来源文档**：Device Access `Device.java`（deviceId 注释"通常为序列号或 MAC"，注册小写化；`ZhenshiMessageHandler` 按 sn 匹配 deviceId）vs 接口规范 §7.2 平台数据模型建议
- **冲突内容**：DA `deviceId` 同时充当 DB 标识与厂商 SN；平台需保留独立主键。

- **推荐 TO-BE**：拆分 `platformDeviceId`（平台主键）/`deviceCode`（可读编码）/`deviceSn`（厂商 SN）。Platform 保留平台主键，调用 DA 传 `deviceSn`；DA 内部以 `deviceSn` 定位设备。相机与道闸分建两个逻辑设备（CAMERA/GATE + executorDeviceId）。
- **决策理由**：不得让同一 deviceId 同时表示平台主键和厂商 SN（AGENTS§9 已要求 device_sn 单独保存）。
- **影响系统**：双方。
- **需双方确认**：是（相机/道闸是否始终分建）。
- **最终状态**：PROPOSED；NEEDS_HUMAN_DECISION（相机/道闸建模）。

## C06 [P1] 设备状态枚举不一致

- **来源文档**：需求规格 §7.9（未激活/在线/离线/故障/禁用/维护中，6 态）vs DA `DeviceStatus`（ONLINE/OFFLINE/UNKNOWN）vs DA `Device.status`（String，注册默认 OFFLINE，枚举未实际使用）

- **决策理由**：单枚举无法表达管理、连接、健康三个正交维度。

## C07 [P0] 开闸无 commandId 幂等，禁止自动重试

- **来源文档**：需求规格（失败自动重试）vs 接口规范 §12（当前无幂等）vs DA 代码（无 commandId）
- **冲突内容**：需求要求失败自动重试，但当前开闸无幂等，盲目重试有重复动作风险。
- **AS-IS**：无 commandId/命令表/幂等；每次调用都执行；超时仅内存 future 丢失。
- **推荐 TO-BE**：命令风险分级——高（开闸/关闸/重启）当前无幂等时网络超时→UNCERTAIN，**禁止自动重试**，人工确认；只有目标版本实现 commandId 幂等+命令查询+明确状态后才按规则重试。HTTP 已受理≠设备成功；命令结果≠闸杆状态。
- **决策理由**：高安全风险，宁可人工兜底不可盲目重试。
- **影响系统**：双方。
- **需双方确认**：是（重试策略）。
- **最终状态**：PROPOSED。

## C08 [P0] 事件传输方式选择

- **来源文档**：接口规范 §19（RabbitMQ 目标）vs T02（RabbitMQ 平台内部）vs DA 代码（无 RabbitMQ）vs 需求 §7.5
- **冲突内容**：方案 A RabbitMQ / B HTTP 回调+Outbox / C 其他。
- **AS-IS**：无事件通道。
- **推荐 TO-BE**：**主通道 RabbitMQ**（device.events.v1 topic exchange，至少一次，平台 Inbox 幂等），HTTP 回调作降级/补偿/排障。不保留多主链路。理由：Platform T02 已用 RabbitMQ 内部；至少一次+Outbox 满足"识别事件不能静默丢失"+离线补传；模块化单体下两人可维护；100 停车场规模 RabbitMQ 足够。HTTP 回调不用于正常识别主链路，仅用于补偿、排障或灾难恢复。
- **决策理由**：可靠投递、去重、离线补传、与平台一致；HTTP 回调作降级保证可用性。
- **影响系统**：双方。
- **需双方确认**：是（主通道最终确认）。
- **是否阻塞最小真机闭环**：是（BLOCKING_FOR_MINIMUM_DEVICE_LOOP）。
- **最终状态**：NEEDS_HUMAN_DECISION（推荐 RabbitMQ）。**状态：PROPOSED。**
