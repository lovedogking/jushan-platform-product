# 01 文档治理

> 文档状态：DRAFT FOR JOINT REVIEW
> 分类：BUSINESS-REQUIREMENT + 元治理

---

## 1. 治理目标

在 Platform 与 Device Access 尚未全部开发完成前，统一双方文档，避免当前实现（AS-IS）与目标设计（TO-BE）混在同一份文档中造成误读。本文件盘点双方已有文档、给出分类与权威状态，并定义冲突处理与变更规则。

本轮**不删除任何历史文档**，只生成新的权威草案与旧文档迁移清单。

## 2. 文档分类定义

| 分类 | 含义 | 状态标记 |
|------|------|----------|
| `BUSINESS-REQUIREMENT` | 平台业务目标和产品范围 | 权威业务边界 |
| `CURRENT-IMPLEMENTED` | 已由代码、测试或真机验证的当前事实 | 仅描述 AS-IS |
| `CURRENT-COMPATIBILITY` | 为兼容当前 Device Access v0.2 保留的临时接口规则 | 临时，待目标版本替代 |
| `TARGET-DRAFT` | 下一阶段双方准备共同实现的目标契约 | `PROPOSED`，未冻结 |
| `VENDOR-REFERENCE` | 厂商 MQTT、HTTP、SDK 等协议资料 | 参考资料，不直接作为平台契约 |
| `DEPRECATED / HISTORICAL` | 历史基线、旧路线图、被替代文档 | 保留，不作为开发依据 |

### 2.1 PROPOSED 与 ACCEPTED 区别

| 状态 | 含义 | 何时可用 |
|------|------|----------|
| `PROPOSED` | 推荐方案，待双方评审确认 | 草案阶段默认状态 |
| `ACCEPTED` | 双方负责人已签署同意 | 仅评审通过后 |
| `FROZEN` | 正式冻结为开发基线 | 仅全部阻塞决策完成 + 双方签署后 |

**关键规则**：
- GLM 或 Claude Code 可给出推荐方案（"推荐……""拟采用……""待双方确认"），但状态必须写 `PROPOSED` 或 `NEEDS_HUMAN_DECISION`；
- **不得**在未经双方负责人签署前使用"已冻结""已确认""双方同意""正式基线""必须按此开发"；
- 若文档描述的是"提案通过后的目标规则"，必须明确标注"本节仅在双方评审通过并升级为 FROZEN 后生效"。

### 2.2 厂商协议能力 ≠ Device Access 实现能力

- 厂商协议支持某功能（如 v1.1.14 §7.19 `gate_direct_open`），不等于 Device Access 已实现；
- 厂商协议为 R3/R5 系列编写，C5H 兼容性未确认；
- Device Access 内部 MQTT 能力（如通用 `publishAndWait`），不等于对 Platform 暴露的 REST 能力；
- 三类能力必须分开描述：厂商能力、Device Access 内部能力、跨系统 REST 能力。

### 2.3 当前代码事实 ≠ 目标设计

- 当前代码实现的模式（如 `deviceId==SN`、`code=200`、无认证），不自动成为目标设计；
- 真机行为只更新厂商映射附录，不应随意改变统一接口语义；
- 当前实现应记录在 `CURRENT-IMPLEMENTED` / `CURRENT-COMPATIBILITY`，目标设计在 `TARGET-DRAFT`。

## 3. 文档优先级（冲突处理规则）

发生冲突时，按以下顺序处理：

1. 用户本次明确要求和已确认的项目业务目标；
2. 平台需求规格说明书中的业务边界（`docs/需求文档/平台侧需求规格说明书.md`）；
3. 本次生成并经双方评审后的共享契约（本目录）；
4. 当前代码和真机行为，用于定义 AS-IS；
5. Device Access 当前 API 文档（`docs/api-v0.2.md`）；
6. 官方厂商协议（`docs/自定义MQTT协议文档v1.1.14.pdf`）；
7. 旧路线图、历史计划和人工提取文档（`docs/mqtt-protocol_p1-10.md`、`docs/device-side/zhenshi-protocol.txt`）。

> 特别注意："真机行为优先"只适用于描述 CURRENT-IMPLEMENTED。它不能自动覆盖 TARGET-DRAFT，也不能把当前技术债永久固化为目标设计。厂商协议支持某功能，不等于 Device Access 已实现。

### Platform 文档要点摘录

- **基础响应与认证契约**（R01 冻结）：统一响应 `code=0` 成功（明确**禁止** `code===200` 旧契约）；字段 `code/message/data/traceId/errors`；认证 `Authorization: Bearer <token>`（Sa-Token）。**适用范围：admin-web、booth-web、miniapp、停车业务平台后端的客户端接口**。它不是 Platform↔Device Access 服务间契约。
- **需求规格说明书 §7.6**：第一阶段支持 远程开闸、远程关闸、远程重启、远程抓拍；同步时间列入"后续预留"。§7.9 设备状态：未激活、在线、离线、故障、禁用、维护中（6 态）。§7.5 事件：按命令类型分结果事件（开闸结果/关闸结果/抓拍结果/重启结果）。
- **T02**：模块化单体；RabbitMQ 仅平台内部；首期约 10 个停车场；不引入微服务/K8s。
- **AGENTS.md §2.2**：将 `POST /api/v1/devices/{deviceSn}/gate/open` 等 3 个 v0.1 接口列为"当前真实接口"，与 Device Access v0.2 代码不一致（见冲突 C01/C05）。

## 6. 厂商协议资料适用范围

厂商 Topic 与字段**只能出现在**：

- Device Access 厂商映射附录（device 分支独立维护）；
- Device Access Adapter 文档；
- 真机验证报告。

**不得**出现在本共享契约的目标接口（TARGET-DRAFT）中。Platform 目标接口不得暴露 `ivs_result`、`gate_direct_open` 等厂商消息名。

不得在厂商 PDF、厂商提取文本（`zhenshi-protocol.txt`）中增加项目结论。

## 7. C5H 与官方协议的兼容性定位

> NEEDS_DEVICE_VERIFICATION

- 官方协议 v1.1.14 主要描述 **R3/R5 系列**车牌识别一体机；
- 项目实际设备为 **臻识 C5H**；
- 不得直接假定 C5H 与 PDF 中全部协议完全兼容；
- 已知差异：`gate_direct_open`（§7.19，v1.1.14 新增）未在 C5H 摄像头订阅列表中发现，导致 Device Access v0.2 移除开闸接口。

真机待确认项（详见 `07-冲突与决策记录.md`）：

- 设备具体型号与固件版本；
- 默认 Topic 与实际启用 Topic；
- C5H 实际开闸机制（gate_direct_open？serial_data？其他？）；
- 字段差异；
- 图片获取方式（云存路径下载？Base64 内容解码？）；
- 离线补传行为；
- 开闸与其他命令回执；
- 心跳频率；
- 道闸状态是否真实可用；
- 关闸命令是否支持。

## 8. 文档版本规则

- 本共享契约整体版本：`v1.0-draft`（评审通过后升级为 `v1.0`）；
- 每份文件头部标注 `文档状态`；
- 机器可读文件（openapi/asyncapi/schemas）含 `version` 字段，须与 Markdown 一致；
- 冻结前，Markdown 与机器可读文件冲突时以 Markdown 为准；冻结后必须同时更新。

## 9. 冻结与变更流程

### 9.1 冻结前

- 任何一方可直接修改草案，但须在 `07-冲突与决策记录.md` 记录变更理由并通知对方。

### 9.2 冻结后（FROZEN v1.0）

- 可新增可选字段；
- 不得重命名已有字段；
- 不得改变已有字段语义；
- 不得删除已有 Routing Key / 路径；
- 破坏性变更必须新建 v2，并提供新旧过渡期；
- 任何变更同步更新 Markdown 与机器可读文件，并经双方评审。
