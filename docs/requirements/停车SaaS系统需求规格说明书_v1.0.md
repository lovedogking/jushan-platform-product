## 1. 引言

### 1.1 编写目的

本文档为停车SaaS系统的需求规格说明书（SRS），旨在明确系统功能边界、业务流程、数据规则及非功能约束，作为产品、开发、测试团队后续工作的统一依据。本文档基于85项需求确认问答整理，所有功能点均已与产品方确认。

### 1.2 项目背景

建设一套面向多租户、多车场的停车SaaS管理系统，支持运营端集中管理、岗亭端现场作业、小程序端车主自助服务，并通过适配器层对接各类停车场硬件设备（相机、道闸等）。

### 1.3 术语定义

| 术语 | 英文 | 定义 |
| :--- | :--- | :--- |
| SaaS | Software as a Service | 软件即服务，本系统以多租户模式向多个停车场提供服务 |
| 租户 | Tenant | 一个停车场或停车场集团，对应一个租户管理员账号 |
| 车场 | Parking Lot | 一个物理停车场，包含若干出入口通道和车位 |
| 通道 | Lane | 车场的物理出入口，可配置为入口、出口或双向通行 |
| 适配器 | Device Access (DA) | 平台与设备之间的中间层，负责协议转换与通信转发 |
| 预订单 | Pre-order | 车辆入场时生成的初始订单，金额尚未计算 |
| 月卡 | Monthly Pass | 按月付费的停车权限，不绑定具体车位号 |
| 固定车位 | Fixed Parking Space | 绑定具体车位号的长期停车权限 |
| 余位 | Available Spaces | 当前可提供给临停车辆的车位数量 |
| RTSP | Real Time Streaming Protocol | 实时流协议，用于视频预览 |
| MQTT | Message Queuing Telemetry Transport | 轻量级消息协议，适配器与设备之间通信 |
| Webhook | Web Hook | HTTP回调机制，适配器向平台推送事件 |
| 岗亭端 | Booth Terminal | 现场保安/收费员使用的Web操作终端 |
| 运营端 | Admin Portal | 平台运营人员和租户管理员使用的Web管理后台 |
| 小程序端 | Mini Program | 车主使用的微信小程序/支付宝小程序 |
| 开闸 | Barrier Open | 控制道闸抬起，允许车辆通行 |
| 关闸 | Barrier Close | 控制道闸落下 |
| 识别事件 | Recognition Event | 相机识别到车牌后产生的事件数据 |
| 黑白名单 | Black/White List | 对特定车牌设置的放行或拦截规则 |
| 模拟支付 | Mock Payment | 本期不对接真实支付渠道，走内部模拟支付流程 |

## 2. 系统概述

### 2.1 系统目标

1. 为停车场运营方提供一套可配置、可扩展的SaaS化管理平台；
2. 支持一个运营平台管理多个租户、多个车场；
3. 通过适配器层解耦平台与硬件设备，便于后续接入不同品牌设备；
4. 为车主提供便捷的自助缴费、月卡办理、余位查询等服务；
5. 为现场管理人员提供实时监控、通行作业、收费处理、交接班等工具。

### 2.2 系统范围

**本期包含：**
- 运营端Web管理后台（车场运营、车辆管理、收费管理、通行记录、数据报表、系统管理）
- 岗亭端Web操作终端（实时监控、通行作业、收费处理、交接班）
- 小程序端车主服务（停车缴费、月卡服务、固定车位、车辆管理、余位查询）
- 平台-适配器-设备通信框架（HTTP REST + Webhook + MQTT）
- 模拟支付全流程

**本期不包含：**
- 优惠券/会员积分系统
- 访客预约管理
- 商家优惠/商家减免
- 真实支付渠道对接（微信支付、支付宝等）
- 电子发票真实开具
- 寻车导航
- 短信推送
- 岗亭端断网离线操作
- 车位地感/检测器硬件对接

### 2.3 系统架构

#### 2.3.1 三端架构

```
┌─────────────────────────────────────────────────────────────┐
│                        用户层                                │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────────┐   │
│  │   运营端      │  │   岗亭端      │  │    小程序端       │   │
│  │  (Web后台)    │  │  (Web页面)    │  │  (微信/支付宝)    │   │
│  └──────┬───────┘  └──────┬───────┘  └────────┬─────────┘   │
└─────────┼────────────────┼──────────────────┼─────────────┘
          │                │                  │
          └────────────────┴──────────────────┘
                             │
                    ┌────────┴────────┐
                    │    平台服务层    │
                    │  (Java/Spring)  │
                    └────────┬────────┘
                             │ HTTP REST (下发)
                             │ HTTP Webhook (上报)
                    ┌────────┴────────┐
                    │    适配器层      │
                    │ (Device Access) │
                    │   HTTP ↔ MQTT   │
                    └────────┬────────┘
                             │ MQTT
                    ┌────────┴────────┐
                    │    设备层        │
                    │ 相机 / 道闸 /   │
                    │ GPIO 控制器     │
                    └─────────────────┘
```

#### 2.3.2 通信架构说明

| 方向 | 协议 | 用途 | 说明 |
| :--- | :--- | :--- | :--- |
| 平台 → 适配器 | HTTP REST | 命令下发 | 设备注册、查询、开闸、校时、状态查询等7个端点 |
| 适配器 → 平台 | HTTP Webhook | 事件上报 | 识别事件、设备状态变化等实时推送 |
| 适配器 → 设备 | MQTT | 设备控制 | 通过 EMQX Broker 与相机/道闸通信 |
| 平台 → EMQX | MQTT | 特殊场景 | 平台直连 EMQX 控制相机 GPIO（开闸/关闸） |

**架构选型理由：**
- 不采用 MQTT 作为平台↔适配器主通信：平台作为 MQTT client 会增加认证、Topic管理、重连逻辑复杂度，当前仅 GPIO 直连 EMQX 为特例。
- 不采用 WebSocket：虽适合实时推送，但命令下发和事件上报的协议精度不如 REST + Webhook 清晰（幂等、重试、鉴权更简单）。
- 当前 v0.2 架构已通过臻识 C5H 真机联调验证。

### 2.4 角色定义

#### 2.4.1 角色总览

| 角色 | 定位 | 创建方式 | 使用终端 |
| :--- | :--- | :--- | :--- |
| 超级管理员 | 平台级最高权限 | 系统预设 | 运营端 |
| 租户管理员 | 车场/租户级管理 | 仅超级管理员创建 | 运营端 |
| 岗亭管理员 | 现场级操作 | 仅超级管理员创建并分配车场 | 岗亭端 |
| 小程序用户 | C端车主 | 微信授权+手机号绑定 | 小程序端 |

#### 2.4.2 超级管理员

- **职责**：全平台数据可见、可创建并管理租户管理员和岗亭管理员、可配置角色权限矩阵、可远程开闸、可配置所有系统参数。
- **权限范围**：全平台所有车场、所有模块。
- **特殊权限**：账号管理、角色权限配置、系统参数配置、远程开闸（全通道）。

#### 2.4.3 租户管理员

- **职责**：管理被分配的车场（一对多）、配置收费规则、管理车辆、查看订单和报表。
- **权限范围**：只能看到被分配车场的数据，超级管理员可配置其可见范围（部分车场/全部车场）。
- **特殊权限**：远程开闸权限由超级管理员单独配置（默认关闭）。

#### 2.4.4 岗亭管理员

- **职责**：管理被分配的多个车场（左侧车场列表切换）、实时监控、通行作业、现场收费、交接班。
- **权限范围**：只能看到所管理车场的数据。
- **特殊权限**：费用减免权限需超级管理员在创建账号时勾选"允许减免"。

#### 2.4.5 小程序用户

- **职责**：自助停车缴费、月卡办理、余位查询、代缴停车费。
- **权限范围**：无后台管理权限，仅操作与自身车辆相关的功能。
- **准入条件**：微信授权登录后必须绑定手机号，否则不可使用核心功能。

## 3. 功能需求

### 3.1 运营端

#### 3.1.1 数据看板

**功能编号**：ADMIN-001  
**功能名称**：首页仪表盘  
**功能描述**：运营端登录后的默认首页，展示核心业务指标。  
**前置条件**：用户已登录且拥有数据看板权限。  
**输入**：无（系统自动加载）。  
**处理流程**：
1. 系统根据用户权限范围（全部/部分车场）聚合数据；
2. 计算今日收入、今日车流量、当前在场车辆数、当前余位数；
3. 统计设备在线/离线数量、未处理异常告警数量。  
**输出**：仪表盘页面，包含上述指标卡片及趋势图表。  
**业务规则**：
- 租户管理员仅展示其被分配车场的数据；
- 数据实时性：收入/流量为实时统计，余位数为定时刷新（按系统参数配置）。

---

#### 3.1.2 车场管理

**功能编号**：ADMIN-002  
**功能名称**：车场基础信息管理  
**功能描述**：对车场的基础信息进行配置和状态管理。  
**前置条件**：超级管理员或租户管理员权限。  
**输入**：
- 车场名称（必填）
- 车场地址（必填）
- 总车位数（必填，正整数）
- 联系人/联系电话（选填）
- 状态：启用/停用  
**处理流程**：
1. 用户填写车场信息并提交；
2. 系统校验总车位数为正整数；
3. 保存车场信息，生成车场ID。  
**输出**：车场列表（支持分页、搜索、筛选、排序）。  
**异常处理**：
- 总车位数非法：提示"总车位数必须为正整数"。  
**业务规则**：
- 停用车场后，该车场不再接收新订单，但历史数据仍可查询；
- 一个租户可管理多个车场（一对多）。

---

#### 3.1.3 区域/车位管理

**功能编号**：ADMIN-003  
**功能名称**：区域划分与车位管理  
**功能描述**：将车场划分为多个区域，配置各区域车位数；管理固定车位绑定。  
**前置条件**：车场已创建。  
**输入**：
- 区域名称（必填）
- 区域车位数（必填）
- 固定车位号（如启用固定车位功能）
- 固定车位绑定车辆（车牌号）  
**处理流程**：
1. 用户创建区域，分配车位数；
2. 系统校验各区域车位数之和 ≤ 车场总车位数；
3. 固定车位需绑定具体车位号和车辆。  
**输出**：区域列表、固定车位列表。  
**业务规则**：
- 固定车位绑定具体车位号，该车位专属此车，其他车辆不能占用；
- 月卡不绑定车位号，仅保证入场权限。

---

#### 3.1.4 出入口管理

**功能编号**：ADMIN-004  
**功能名称**：出入口通道配置  
**功能描述**：配置车场的出入口通道基本信息及通行方向。  
**前置条件**：车场已创建。  
**输入**：
- 通道名称（必填）
- 通道类型：入口 / 出口 / 双向通行（必填）
- 关联区域（选填）  
**处理流程**：
1. 用户创建通道并配置类型；
2. 系统保存通道信息。  
**输出**：通道列表。  
**业务规则**：
- 通道类型支持双向通行，同一通道既可进也可出；
- 通道需绑定相机后才能正常使用。

---

#### 3.1.5 设备管理

**功能编号**：ADMIN-005  
**功能名称**：出入口相机绑定与管理  
**功能描述**：对出入口相机进行绑定、解绑、配置主备关系、远程校时、状态监控。  
**前置条件**：通道已创建。  
**输入**：
- 相机IP地址（必填）
- 端口号（必填）
- 用户名/密码（必填）
- 所属车场（自动关联）
- 所属通道（必填）
- 相机编号/名称（必填）
- 主备关系：主相机 / 备相机（双相机模式时配置）  
**处理流程**：
1. 用户填写相机信息并绑定到通道；
2. 系统校验IP格式和端口合法性；
3. 保存相机信息，尝试连接测试；
4. 支持远程校时（平台 HTTP REST → 适配器 → 设备）。  
**输出**：设备列表（含在线/离线状态）。  
**异常处理**：
- 相机连接失败：标记为离线，触发告警。  
**业务规则**：
- 必须支持单相机模式和双相机模式；
- 双相机模式需指定主备关系，主相机故障时自动切换备相机；
- 设备离线时运营端弹窗告警，同时岗亭端弹窗提示。

---

#### 3.1.6 月卡管理

**功能编号**：ADMIN-006  
**功能名称**：月卡登记、续期与注销  
**功能描述**：对月卡车辆进行全生命周期管理。  
**前置条件**：车场已创建。  
**输入**：
- 车牌号（必填）
- 车辆类型（小型车/大型车等，选填）
- 有效期起止（必填）
- 费用（必填）
- 关联车场（必填）  
**处理流程**：
1. 用户录入月卡信息或审核小程序端申请；
2. 系统校验车牌号唯一性（同一车场内同一车牌不能重复办理）；
3. 保存月卡信息，状态为"生效中"。  
**输出**：月卡列表（支持到期预警筛选）。  
**异常处理**：
- 车牌重复：提示"该车场已存在该车牌的月卡"。  
**业务规则**：
- 月卡状态：生效中 / 已过期 / 已注销；
- 到期后自动失效，车辆按临停计费；
- 到期前提醒天数可配置（系统参数）；
- 小程序端可申请月卡，运营端审核流程可配置（部分车场需审核，部分自动通过）。

---

#### 3.1.7 固定车位管理

**功能编号**：ADMIN-007  
**功能名称**：固定车位绑定与管理  
**功能描述**：管理固定车位与车辆的绑定关系。  
**前置条件**：区域/车位已创建。  
**输入**：
- 车位号（必填）
- 车牌号（必填）
- 有效期起止（必填）
- 费用（必填）  
**处理流程**：
1. 用户选择车位号并绑定车辆；
2. 系统校验车位号未被占用；
3. 保存绑定关系。  
**输出**：固定车位列表。  
**业务规则**：
- 固定车位绑定具体车位号，该车位专属此车；
- 到期管理与月卡分开处理；
- 固定车位状态：生效中 / 已过期 / 已注销。

---

#### 3.1.8 黑白名单管理

**功能编号**：ADMIN-008  
**功能名称**：黑白名单配置  
**功能描述**：对特定车牌设置放行或拦截规则。  
**前置条件**：车场已创建。  
**输入**：

### 3.4 平台-适配器-设备通信

#### 3.4.1 命令下发接口

**功能编号**：COMM-001  
**功能名称**：平台到适配器的命令下发  
**功能描述**：平台通过HTTP REST接口向适配器下发设备控制命令。  
**接口协议**：HTTP REST  
**接口端点**：
- POST /api/v1/device/register — 设备注册
- GET /api/v1/device/{id} — 设备查询
- POST /api/v1/device/{id}/open — 开闸
- POST /api/v1/device/{id}/close — 关闸
- POST /api/v1/device/{id}/sync-time — 校时
- GET /api/v1/device/{id}/status — 状态查询  
**请求参数**：设备ID、通道ID、车场ID等。  
**响应格式**：JSON，包含状态码、消息、数据。  
**业务规则**：
- 幂等性：重复下发同一命令，设备直接响应，无副作用；
- 超时重试：适配器未响应时平台自动重试（3次）。

---

#### 3.4.2 事件上报接口

**功能编号**：COMM-002  
**功能名称**：适配器到平台的事件上报  
**功能描述**：适配器通过HTTP Webhook向平台推送设备事件。  
**接口协议**：HTTP Webhook  
**上报事件类型**：
- 车牌识别事件（含车牌号、通道、时间、抓拍图片URL）
- 设备状态变化（在线/离线）
- 道闸状态变化（开/关）  
**请求格式**：JSON Payload。  
**响应要求**：平台返回200表示接收成功，适配器未收到200则重试。  
**业务规则**：
- 识别事件实时推送，延迟要求 < 2秒；
- 平台需校验Webhook请求签名，防止伪造。

---

#### 3.4.3 适配器到设备通信

**功能编号**：COMM-003  
**功能名称**：适配器到设备的MQTT通信  
**功能描述**：适配器通过MQTT协议与相机、道闸等设备通信。  
**协议**：MQTT 3.1.1  
**Broker**：EMQX  
**Topic设计**：
- 命令下发：device/{device_id}/command
- 状态上报：device/{device_id}/status
- 识别事件：device/{device_id}/recognition  
**QoS**：命令下发 QoS 1，状态上报 QoS 0。  
**业务规则**：
- 适配器作为MQTT Client连接EMQX；
- 设备（相机）作为MQTT Client连接EMQX；
- 平台仅在GPIO特殊场景下直接连接EMQX。

## 7. 业务规则

### 7.1 计费规则

1. **免费时长**：入场时标记免费，超期后从免费时长结束后开始计费（前X分钟不计入）。
2. **跨天计费**：可配置为按自然日分段（每天0点重置）或连续计费（总时长计算）。
3. **封顶计费**：24小时封顶金额，超出后按天重新计算或继续累计（按配置）。
4. **时段阶梯**：不同时间段可设置不同费率，支持多时段配置。
5. **收费规则生效**：可选择立即生效（已入场车辆也按新规则）、仅新入场生效（已在场车辆按旧规则）、定时生效（未来时间点生效）。

### 7.2 开闸规则

1. **自动开闸条件**：月卡/固定车位在有效期内、白名单车辆、已支付订单、免费放行。
2. **未支付拦截**：出场时存在未支付订单，按车场配置处理：拦截（不开闸）或允许欠费（开闸但标记欠费）。
3. **手动开闸**：必须输入放行原因，可选择是否计费。
4. **远程开闸**：运营端操作后，岗亭端弹窗提示。
5. **开闸幂等性**：重复下发同一开闸指令，设备直接响应，无副作用。

### 7.3 订单规则

1. **订单生成**：车辆入场时生成预订单，出场时更新为正式订单并计算金额。
2. **模拟支付**：用户点击"确认支付"即模拟支付成功，订单状态更新为"已支付"。
3. **支付超时**：按车场配置的超时时间，超时后订单可手动关闭或自动关闭。
4. **代缴规则**：任何人可代缴任意车牌，支付记录归实际支付人，通知双方。

### 7.4 车辆管理规则

1. **月卡**：不绑定车位号，仅保证入场权限，到期后自动失效转临停计费。
2. **固定车位**：绑定具体车位号，该车位专属此车，其他车辆不能占用。
3. **黑白名单**：互斥，同一辆车不允许同时存在于黑白名单中。
4. **黑名单触发**：可配置为禁止入场、允许入场但告警、或按类型区分。

### 7.5 数据隔离规则

1. **超级管理员**：全平台数据可见。
2. **租户管理员**：仅可见被分配车场的数据，超级管理员可配置其可见范围。
3. **岗亭管理员**：仅可见所管理车场的数据。
4. **小程序用户**：仅可见与本人绑定车辆相关的数据。

## 10. 附录

### 10.1 核心业务流程图（文字描述）

#### 临停车辆入场流程
```
车辆到达入口 → 相机识别车牌 → 适配器MQTT接收 → Webhook上报平台
→ 平台校验（黑名单/月卡/白名单/临停） → 生成预订单 → HTTP REST下发开闸
→ 适配器MQTT转发 → 道闸开启 → 余位更新 → 记录通行记录
```

#### 临停车辆出场流程
```
车辆到达出口 → 相机识别车牌 → Webhook上报平台 → 查找预订单
→ 计算费用 → 订单状态更新为"待支付"
→ 未支付处理：按配置拦截或允许欠费
→ 小程序支付：确认支付 → 模拟支付成功 → 订单"已支付" → 自动开闸
→ 出场记录更新 → 余位更新
```

#### 手动开闸流程
```
岗亭管理员点击手动开闸 → 选择通道（支持批量） → 输入放行原因
→ 选择是否计费（计费输入金额/免费） → 确认开闸
→ HTTP REST下发 → 适配器MQTT转发 → 道闸开启 → 记录手动开闸日志
```

#### 运营端远程开闸流程
```
运营端选择通道 → 点击远程开闸 → 输入原因 → HTTP REST下发到适配器
→ 适配器MQTT转发到设备 → 道闸开启 → 实时通知岗亭端弹窗
→ 岗亭端显示：操作人、时间、通道、原因 → X秒后自动消失
```

#### 月卡办理流程
```
小程序：选择车场 → 填写车辆信息 → 提交申请
运营端：按车场配置自动通过或人工审核
小程序：查看审核状态（不主动推送）
→ 审核通过 → 月卡"生效中" → 到期自动失效转临停
```

#### 模拟支付流程
```
出场识别/小程序查询 → 订单"待支付" → 小程序点击"确认支付"
→ 系统模拟支付成功 → 订单"已支付" → 自动开闸 → 推送支付成功通知
→ 订单"已完成"
```
