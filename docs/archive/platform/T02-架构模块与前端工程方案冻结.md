### 5.1 不采用的方案

| 方案 | 理由 |
|------|------|
| Spring Cloud / 微服务 | 首期约 10 个停车场，模块化单体足够；过早微服务化违反需求原则 |
| Kubernetes | 超出第一阶段范围，试运营仅需单机 Docker Compose |
| 更换数据库（PostgreSQL/Oracle） | 需求明确 MySQL 8.x |
| 更换主框架（Quarkus/Micronaut） | 团队技术栈为 Spring Boot |
| 引入 DDD 复杂框架（Axon/Eventuate） | 模块化单体 + 应用服务 + 领域服务分层足够 |

### 7.1 依赖层次

```

parking-module-system → parking-framework
parking-module-tenant → parking-framework + parking-module-system
parking-module-parking-lot → parking-framework + parking-module-tenant
parking-module-device → parking-framework + parking-module-parking-lot
parking-module-record → parking-framework + parking-module-parking-lot + parking-module-device
parking-module-charge → parking-framework + parking-module-parking-lot
parking-module-order  → parking-framework + parking-module-record + parking-module-charge
parking-module-payment → parking-framework + parking-module-order + parking-module-tenant
parking-module-member → parking-framework + parking-module-user + parking-module-charge
parking-module-coupon → parking-framework + parking-module-parking-lot
parking-module-user   → parking-framework + parking-module-tenant
parking-module-notice → parking-framework + parking-module-user
parking-module-report → parking-framework + parking-module-record + parking-module-order + parking-module-payment
parking-module-extension → parking-framework（仅接口抽象，不依赖其他业务模块）
```

### 7.3 模块间通信规则

| 规则 | 说明 |
|------|------|
| ✅ 通过公开 Service/Facade 调用 | 模块对外暴露 `XxxService` 或 `XxxFacade` 接口 |
| ✅ 通过领域事件协作 | 模块间异步解耦：发布事件 → 消费事件 |
| ❌ 禁止跨模块直接操作 Mapper | 如 `order` 模块不能直接调用 `payment` 模块的 `PaymentMapper` |
| ❌ 禁止跨模块直接修改数据库实体 | 如 `record` 模块不能直接 `UPDATE payment` 表 |
| ❌ 禁止循环依赖 | Maven `requires` 不得形成环 |

### 7.4 关键禁止依赖（P0）

```
┌──────────────────────────────────────────────────┐
│ ✗ parking-module-payment → parking-module-device  │  支付模块禁止调用 Device Access
│ ✗ parking-module-device  → parking-module-payment │  设备模块禁止修改支付状态
│ ✗ parking-module-device  → parking-module-order   │  设备模块禁止修改订单金额/状态
│ ✗ 任何业务模块 → 直接操作其他模块 Mapper           │
└──────────────────────────────────────────────────┘
```

验证方法：
```bash

mvn dependency:tree -Dverbose | grep -E "parking-module-device.*parking-module-payment|parking-module-payment.*parking-module-device"
```

## 8. 模块公开 Facade/Service 边界（冻结）

### 8.1 跨模块调用约定

每个业务模块通过**公开 Service 接口**对外暴露能力：

```java
// 示例：parking-module-device 对外暴露
package com.jushan.device.application.service;

public interface DeviceAccessService {
    /**
     * 通过平台设备主键开闸。
     * 内部完成：权限校验、SN 查证、调用 Device Access、审计。
     * 返回调用结果（SUCCESS / FAILED_* / UNCERTAIN）。
     */
    DeviceCallResult openGate(Long platformDeviceId, OpenGateContext ctx);
}
```

调用方模块通过 Spring DI 注入公开 Service，**不得**直接 import 被调用模块的 Mapper 或 Entity。

### 8.2 模块公开接口清单（骨架，T04 后逐步实现）

| 模块 | 对外公开 Service/Facade | 用途 |
|------|------------------------|------|
| system | `AccountService`, `RoleService`, `PermissionService` | 用户、角色、权限查询和校验 |
| tenant | `TenantService`, `TenantContextService` | 租户查询、可信上下文、数据范围 |
| parking-lot | `ParkingLotService`, `LaneService`, `ReadinessService` | 停车场、车道查询、就绪检查 |
| device | `DeviceAccessService`, `DeviceQueryService` | 开闸、校时、状态查询、SN 查证 |
| record | `RecordService`, `ParkingRecordService` | 停车记录查询、在场统计、出入场 |
| charge | `ChargeRuleService`, `CalculateService` | 收费规则查询、计费计算 |
| order | `OrderService`, `OrderStateService` | 订单创建、状态查询、费用预览 |
| payment | `PaymentGatewayService`, `PaymentCallbackService` | 预支付、回调处理（不公开给 device） |
| member | `MemberService`, `MonthlyCardService` | 身份判定、月卡有效性 |
| coupon | `CouponService` | 券领取、锁定、核销 |
| user | `UserService`, `VehicleService` | 车主查询、车辆绑定、无牌凭证 |
| notice | `NoticeService` | 发送订阅消息 |
| report | `ReportService` | 统计查询（只读） |
| extension | 仅接口抽象 | 预约/共享停车占位契約 |

## 9. 前端工程划分（冻结）

### 9.1 工程划分

```
jushan-platform/
├── admin-web/        # 统一管理后台 → 承载总后台 + 运营端
├── booth-web/        # 岗亭端（独立部署）
└── miniapp/          # 原生微信小程序
```

### 9.2 admin-web 详细设计

| 维度 | 方案 |
|------|------|
| 框架 | Vue 3 (Composition API) + TypeScript + Vite + Pinia + Vue Router + Arco Design Vue |
| 承载端 | **统一承载**总后台 + 运营端，通过角色路由和数据范围隔离 |
| 角色路由 | 总后台路由（`/admin/**`）vs 运营端路由（`/operator/**`） |
| 登录入口 | 统一登录页，根据账号角色自动路由到对应端 |
| 权限模型 | 后端 Sa-Token + 前端路由守卫 + 按钮级 `v-permission` 指令 |
| API 封装 | `@/utils/request` 统一拦截：TraceId 注入、401→登录页、错误统一提示 |
| 状态管理 | Pinia：`useUserStore`（用户/角色/权限）、`useTenantStore`（当前租户/停车场范围） |

**为什么 admin-web 不拆分为两个工程？**

- 总后台和运营端共享大量组件（表格、表单、权限控制、布局）
- 首期约 10 个停车场，拆分维护成本高于收益
- 角色路由 + 数据范围隔离已能满足安全要求
- 后续如总后台功能激增，可按路由组拆分为独立部署

### 9.3 booth-web 详细设计

| 维度 | 方案 |
|------|------|
| 框架 | 同 admin-web（Vue 3 + Arco Design Vue） |
| 部署 | **独立部署**，不混入管理后台 |
| 理由 | 岗亭端涉及高风险开闸操作和实时页面，独立部署降低管理端改动影响；岗亭可独立扩缩容 |

**功能范围：**
- 实时入场/出场推送（WebSocket）
- 车辆通行记录列表/详情
- 车牌修正
- 人工放行/人工减免
- UNCERTAIN 开闸处置
- 设备状态/告警查询
- 断线重连 + 增量恢复游标

**禁止功能（第一阶段）：**
- 现金收费
- 交接班
- 切换收费规则
- 停用停车场
- 修改支付配置

### 9.4 miniapp 详细设计

| 维度 | 方案 |
|------|------|
| 框架 | 原生微信小程序（不使用 uni-app / Taro） |
| 优点 | 体积小、启动快、微信 API 直接调用、依赖最少 |
| 登录流程 | `wx.login()` → 平台后端换取 token |

**功能范围（第一阶段）：**

### 9.6 前端禁止事项

| 禁止 | 理由 |
|------|------|
| 前端直传 `tenantId` / `parkingLotId` | 后端从可信上下文获取 |
| 前端直传 `deviceSn` | 后端根据平台设备 ID 查证 SN |
| 管理后台/小程序直接调用 Device Access | Device Access 仅后端内网调用 |
| 前端隐藏按钮代替后端鉴权 | P0 红线 |
| `admin-web` 硬编码基站 URL 指向生产 | 通过环境变量注入 |
