## 使用说明（先读）

1. **一次一包**：每个任务包开一个新会话执行，把任务包全文粘贴给 AI（Claude Code / Qoder 均可）。不要一次喂多包。
2. **顺序执行**：阶段 0 → 5 按编号来，验收不过不进下一包。同阶段内可按标注并行。
3. **前提**：把《停车SaaS系统需求规格说明书 V1.1》放到仓库 `docs/需求文档/` 下，并在 claude.md / AGENTS.md 中声明其为唯一需求事实源（任务包内引用章节号即指该文档）。
4. **验收方式**：每包末尾的"验收标准"逐条人工核对；附录 10.1 流程图是整体验收剧本。
5. **Commit 规范**：`feat(功能编号): 描述` 或 `refactor(模块): 描述`，一包一个 commit。

# 阶段 0：重构收敛（双包合并）

> 目标：消除 com.jushan.system（旧）与 com.jushan.platform.modules（新）双包并存，让后续 V1.1 功能有唯一落脚点。此阶段不改任何业务行为。

## 任务包 0-1：冻结旧包、建立迁移映射

```
【任务包 0-1】冻结旧包 com.jushan.system，输出迁移映射表

背景：仓库存在双包结构——旧包 com.jushan.system 装着核心业务（ParkingOrder、
PayOrder、Device、ExitService、WebSocket 等），新包 com.jushan.platform.modules
是 Sprint 1 重构目标。本任务只做盘点与冻结，不做代码迁移。

目标：
1. 在旧包 com.jushan.system 的包级添加 @Deprecated 标记与注释：
   "本包已冻结，只删不增，业务迁移至 com.jushan.platform.modules"
2. 盘点旧包中所有 public 类（entity/service/controller/ws/event），
   输出《迁移映射表.md》到 docs/，格式：
   | 旧包类 | 新包对应类（已有/待建） | 依赖它的类 | 建议迁移批次 |
3. 检查 Spring 扫描配置，确认新旧两包当前都被扫描，列出所有引用旧包类的位置清单

约束：
- 不修改任何业务逻辑、不移动任何文件
- 不改变任何接口行为

验收标准：
1. 项目编译通过、已有测试全绿
2. docs/ 下生成迁移映射表，覆盖旧包全部 public 类
3. 旧包每个包都有明确的冻结标记
```

## 任务包 0-2：计费规则双份收敛为一套

```
【任务包 0-2】计费规则收敛：FeeRule（新包）与 BillingRule（旧包）合并为一套

需求依据：V1.1 第 3.1.10 节（ADMIN-010）、业务规则 7.1

背景：新包 parking.entity.FeeRule（+FeeRuleSegment）与旧包 system.entity.BillingRule
（+BillingRuleVersion 等）并存，两处计费规则会导致收费口径不一致。

目标：
1. 对照 V1.1 ADMIN-010 的输入项（计费方式：按分钟累计/按时段阶梯/封顶计费；
   免费时长；跨天规则；生效方式：立即/仅新入场/定时），确定唯一保留的模型
   （默认保留新包 FeeRule，缺口从新包补齐字段）
2. 旧包 BillingRule 的调用方（计费、出场、订单）全部切换到新包 FeeRule
3. 旧 BillingRule 表数据通过 Flyway 迁移脚本搬到新表（如有存量数据）
4. 旧包 BillingRule 相关类标记 @Deprecated，保留只读

约束：
- 数据库变更只新增 Flyway 脚本，禁止修改已执行脚本
- 切换后计费结果对存量场景保持一致（列出对比自测用例）
- 不引入新依赖

验收标准：
1. 全系统只有一套计费规则模型被引用
2. 三种计费方式 + 免费时长 + 跨天规则 + 三种生效方式均有单测覆盖并通过
3. 旧计费入口全部下线或委托给新实现
```

# 阶段 1：地基（状态机 + 参数体系 + 三个实体重建）

> 目标：把 V1.1 要求而代码里不存在的数据模型全部补齐。本阶段只动后端模型与接口，不动前端页面。

## 任务包 1-1：订单状态机扩展（预订单 + 欠费中）

```
【任务包 1-1】ParkingOrder 状态机扩展：增加预订单与欠费中

需求依据：V1.1 第 7.3 条、附录 10.2 临停订单状态机、6.1 数据字典订单状态

目标：
1. ParkingOrder 增加状态：PRE_ORDER（预订单）、ARREARS（欠费中）
2. 状态流转按 V1.1 附录 10.2 实现：
   PRE_ORDER --出场计费--> PENDING_PAY --支付--> PAID --出场完成--> COMPLETED
   PENDING_PAY --超时关闭--> CANCELLED
   PENDING_PAY --允许欠费--> ARREARS --补缴--> COMPLETED
   PAID --退款(模拟)--> REFUNDED
   PRE_ORDER --免费放行--> COMPLETED
3. 入场时为临停车辆生成 PRE_ORDER 订单（月卡/固定车位/白名单仅生成通行记录）
4. 退款增加前置校验：仅 PAID 状态可发起，记录退款原因，本期为模拟退款
   （仅状态流转与记录，无真实资金）
5. 增加状态流转日志（来源状态、目标状态、操作人/触发源、时间）

约束：
- 历史数据兼容：存量 PENDING_PAY 订单不受影响，无需数据订正（说明理由）
- Flyway 新增脚本，不改旧脚本
- 状态机用枚举/常量集中管理，禁止散落字符串

验收标准：
1. 6 条流转路径各有单测并通过
2. 非法流转（如 CANCELLED → PAID）被拦截并抛业务异常
3. 退款从非 PAID 状态发起时被拒绝
```

## 任务包 1-2：两层参数体系（全局参数 + 车场级参数）

```
【任务包 1-2】系统参数模块：全局参数 + 车场级参数两层体系

需求依据：V1.1 第 3.1.20（ADMIN-020）、3.1.02（ADMIN-002 车场级参数表）、6.1 数据字典

目标：
1. 新建参数表（sys_parameter）：参数键、参数值、参数层级（1=全局/2=车场级）、
   车场ID（车场级时非空）、说明、默认值
2. 内置全局参数（默认值）：
   - 余位刷新间隔 5分钟
   - 车辆绑定数量上限 3辆
   - 远程开闸弹窗自动消失时长 10秒
   - 大额收费二次确认阈值 100元
   - 黑名单触发模式 禁止入场/允许入场但告警/按类型区分
3. 内置车场级参数（默认值，在车场设置中维护）：
   - 模拟支付超时时间 15分钟
   - 未支付出场策略 拦截/允许欠费（默认拦截）
   - 欠费车辆再次出场策略 必须补缴/仅提醒（默认必须补缴）
   - 识别失败处理策略 转人工/自动放行（默认转人工）
   - 月卡到期提醒天数 7天
   - 月卡/固定车位是否计入余位 计入
   - 支付后出场窗口期 15分钟
4. 提供参数读取服务：按"车场级优先、缺省回退全局/默认值"解析
5. 提供运营端参数管理接口（全局参数 CRUD + 车场参数按车场读写）

约束：
- 参数读取走缓存（遵循项目现有缓存方案），变更后立即失效
- 参数键用常量类集中定义，禁止魔法字符串
- 不改动现有 AccessPolicy 散装配置（后续任务统一收口时再评估）

验收标准：
1. 两层参数均可读写，车场级覆盖全局的优先级逻辑有单测
2. 修改参数后读取方立即拿到新值
3. 接口有权限控制（仅超级管理员）
```

# 阶段 2：收费闭环（V1.1 四大缺口）

> 目标：补齐出场窗口期、超时重计费、欠费链路、模拟退款。依赖阶段 1 的状态机与参数体系。

## 任务包 2-1：支付出场窗口期

```
【任务包 2-1】区分出口缴费与提前缴费：支付出场窗口期

需求依据：V1.1 第 3.3.3（MINI-003）、7.2-7、附录出场流程图

目标：
1. 订单增加字段：支付窗口截止时间（pay_deadline）
2. 支付成功后的开闸逻辑分两种场景：
   - 出口缴费（订单由出口识别触发，车辆已在出口）：支付成功立即触发开闸
   - 提前缴费（车辆未在出口）：支付成功写入 pay_deadline =
     当前时间 + 车场级参数"支付后出场窗口期"（默认15分钟）
3. 出口识别时的判断：
   - 存在已支付订单且当前时间 ≤ pay_deadline → 自动开闸
   - 已支付但已超过 pay_deadline → 按计费规则重新计算费用，
     生成新的待支付订单（原订单保持已支付/已完成状态，报告中说明口径）
4. 开闸调用走平台→适配器接口（适配器未就绪时用 Mock 适配器响应，
   保证链路可自验）

约束：
- 窗口期时长读取任务包 1-2 的车场级参数，改参即生效
- 不改动月卡/白名单的自动放行逻辑

验收标准：
1. 三种场景（出口缴费立即开闸/窗口期内出场开闸/超期重计费）
   各有集成测试并通过
2. pay_deadline 计算随参数修改生效
3. 全流程可用 Mock 适配器跑通
```

## 任务包 2-2：待支付超时关闭 + 重新计费

```
【任务包 2-2】待支付订单超时关闭后重新计费

需求依据：V1.1 第 3.1.12（ADMIN-012）、7.3-3

目标：
1. 定时任务扫描待支付订单：超过车场级参数"模拟支付超时时间"
   （默认15分钟）未支付的，自动关闭为已取消
2. 车辆再次被出口识别时：若存在已取消的历史待支付订单且无有效订单，
   按当前计费规则以实际停车时长重新计算费用，生成新的待支付订单
3. 重新计费留痕：记录重算日志（原订单号、原金额、新金额、触发原因）
   ——可复用现有 billing_rule_recalc_log 表结构评估后扩展

约束：
- 定时任务用项目现有调度方案（xxl-job/@Scheduled，遵循现状）
- 幂等：同一车辆同一在场记录不会生成两张有效待支付订单
- 月卡/白名单/固定车位车辆不进入该逻辑

验收标准：
1. 超时订单被自动关闭（任务触发验证）
2. 再次识别后新订单金额 = 按实际时长重算（测试用例覆盖）
3. 幂等性测试通过（重复识别不产生重复订单）
```

## 任务包 2-3：欠费链路

```
【任务包 2-3】欠费全链路：欠费出场 → 展示 → 补缴 → 再出场拦截

需求依据：V1.1 第 7.2-2、7.2-3、3.3.9（MINI-009）、附录欠费补缴流程图

目标：
1. 出场时未支付处理按车场级参数"未支付出场策略"执行：
   - 拦截（默认）：不开闸，提示待支付
   - 允许欠费：开闸，订单置为 ARREARS（欠费中），记录欠费放行日志
2. 欠费车辆再次入场：正常识别入场（生成新预订单）

约束：

验收标准：
```
