## 二、五大关键发现（附证据）

### 发现 1：双包结构并存，是当前最大的工程风险 🔴

同一实体一式两份，例如：
- 旧包：`com/jushan/system/entity/ParkingLot.java`、`ParkingLane.java`、`Company.java`、`Tenant.java`
- 新包：`com/jushan/platform/modules/parking/entity/ParkingLot.java`、`ParkingLane.java`、`company/entity/SysCompany.java`、`tenant/entity/SysTenant.java`

核心业务（订单 ParkingOrder、支付 PayOrder、设备 Device、出场 ExitService、WebSocket 推送）全部还在旧包；新包是 Sprint 1 重构的目标结构。**重构没收尾前按 V1.1 开发，新功能归属会混乱，越写越难收。**

### 发现 2：收费闭环四个 V1.1 关键点全部缺失 🔴

| V1.1 要求 | 代码证据 | 状态 |
| :--- | :--- | :--- |
| 出场窗口期（7.2-7） | 全仓检索 grace/window **0 命中** | 未实现 |
| 欠费链路（7.2-3） | 全仓检索 arrears/debt **0 命中**；ParkingOrder 状态机无"欠费中" | 未实现 |
| 超时关单重新计费（7.3-3） | ParkingOrder 有 `expiredAt` 字段，但无重新计费逻辑 | 未实现 |
| 预订单状态（7.3-1） | 现有状态：PENDING_PAY / PAYING / PAID / COMPLETED / CANCELLED / PAY_FAILED / REFUNDING / REFUNDED，**无 PRE_ORDER（预订单）、无 ARREARS（欠费中）** | 状态机需扩展 |

注：退款状态（REFUNDING/REFUNDED）已存在，是好的基础，但需补"仅已支付可退"的约束校验。

### 发现 3：月卡与固定车位模型与 V1.1 不符，需重建地基 🔴

**月卡现状**（`platform/modules/vehicle/entity/SysVehicle.java`）：
月卡只是车辆的一个类型标签 `vehicleType = MONTHLY`，附带 validStartDate / validEndDate。**V1.1 要求的独立月卡实体、审核流（自动通过/人工审核可配置）、缴费方式登记、月卡订单、与固定车位分开的过期管理，全部不存在。**

**固定车位现状**（`platform/modules/parking/entity/ParkingSpacePolicy.java`）：
只有区域车位**数量策略**（totalSpaces / fixedSpaces / tempSpaces / reservedSpaces / 满位动作）。**V1.1 要求的"车位号绑定车辆 + 有效期 + 费用 + 独立生命周期"模型不存在。**

### 发现 4：名单体系与系统参数整体缺失 🔴

- 黑名单：以 `AccessPolicy` 泛化 key-value 策略存在（policyType=BLACKLIST），但**白名单 0 命中、黑白名单互斥校验无、类型字典（欠费类/管理类/其他类）无、有效期无**。
- 系统参数：检索 sys_config / SysConfig / SystemParam **0 命中**。V1.1 要求的全局参数（ADMIN-020）+ 车场级参数（ADMIN-002 参数表）两层体系没有落脚处，当前只有 AccessPolicy 的散装 key-value。

### 发现 5：设备链路断在适配器，平台侧无法闭环 🟡

- `DeviceController`（旧包）端点：列表/详情/增改/状态/绑定车道/厂商型号/**校时**——**没有开闸端点**。
- `ExitService.java` 第 39 行注释明写："不直接调用 Device Access 开闸（gate/open 在 v0.2 中未实现）"。
- 结论：ADMIN-022 远程开闸、支付后自动开闸、识别事件驱动的进出场主链路，**瓶颈全部在 Device Access 侧**（需从 v0.2 升级到含开闸 + Webhook 事件上报的版本）。平台侧能做的是先按 V1.1 契约把调用层和 Webhook 接收端写好、用 Mock 跑通。

## 四、需要你决策的三个问题

1. **Pyun（P云）支付代码去留**：V1.1 规划三期才接真实支付，但仓库已有 3 个 P云 Controller。建议：保留但隔离，标记为三期代码、不进本期主链路，并在 claude.md 注明"本期任务不得改动 Pyun 相关代码"。
2. **双包收敛方向**：建议按 README 既定 Sprint 1 方向走——业务迁往 `com.jushan.platform.modules`，旧包 `com.jushan.system` 冻结为只删不增。反向操作（回旧包）等于推翻 Sprint 1 已投入的工作。
3. **Device Access 升级节奏**：开闸 + Webhook 事件上报是主链路的前提。平台侧可以先按 V1.1 契约把调用层/Webhook 接收端写好并用 Mock 自验，不必等设备侧，但**联调排期要以适配器 v1.0 就绪为节点**。
