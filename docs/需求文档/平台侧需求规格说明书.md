# 智慧停车 SaaS 平台需求规格说明书

> 文档版本：V1.0  
> 文档状态：需求确认版  
> 项目类型：多租户、公有云智慧停车 SaaS 平台  
> 首期规模：预计接入约 10 个停车场，架构预留扩展至 100 个停车场  
> 首期设备厂商：臻识、信路通  
> 编制日期：2026-07-10

---

## 1. 文档说明

### 1.1 编写目的

本文档用于明确智慧停车 SaaS 平台的建设目标、业务范围、用户角色、功能需求、核心流程、数据规则、设备接入规范、安全要求、非功能要求、技术架构、上线策略和验收标准。

本文档作为以下工作的共同依据：

- 产品原型设计；
- 系统架构设计；
- 数据库设计；
- 接口设计；
- 前后端开发；
- 设备厂商联调；
- 微信支付联调；
- 测试用例设计；
- 试运营验收；
- 正式商用上线。

### 1.2 项目定义

本项目建设一套基于 Java 的多租户智慧停车 SaaS 平台，为平台运营方、停车场客户、停车场管理人员、岗亭工作人员和普通车主提供停车场配置、设备接入、车辆通行、停车计费、微信支付、月卡、优惠券、欠费补缴、设备运维和经营统计等能力。

系统由以下业务端组成：

1. 总后台：平台方超级管理员及平台运营人员使用；
2. 运营端：停车场客户及其员工使用；
3. 岗亭端：停车场现场工作人员使用；
4. 微信小程序：普通车主使用；
5. 统一 Java 后端：承载业务、权限、计费、订单、支付、设备、消息及数据能力。

### 1.3 需求原则

系统建设遵循以下原则：

- 真实停车场落地优先于版本和技术新颖度；
- 车辆通行安全优先于 SaaS 商业限制；
- 支付、计费和开闸必须可追溯、可重试、可补偿；
- 多租户、停车场和设备数据必须由后端强制隔离；
- 厂商设备必须通过统一适配层接入；
- 第一阶段采用模块化单体，避免过早微服务化；
- 关键规则尽量配置化，但必须提供安全默认值和权限约束；
- 第一阶段先满足受控试运营，再逐步开放正式商用。

## 2. 项目背景与建设目标

### 2.1 项目背景

停车场业务涉及车牌识别、设备通信、车辆通行、收费规则、微信支付、现场应急和多角色管理。不同厂商相机和道闸协议不一致，停车场经营规则也存在较大差异，因此系统需要同时具备标准化核心业务能力和灵活配置能力。

项目首先面向平台自营的公有云 SaaS 场景，为不同停车场客户提供统一系统。后续可扩展为客户本地私有化部署，但不属于第一阶段交付范围。

### 2.2 总体目标

系统需要实现以下总体目标：

1. 支持平台统一管理客户、停车场、设备、订单、支付和运营数据；
2. 支持客户注册并经平台审核后开通运营端；
3. 支持一个客户管理多个停车场；
4. 支持停车场配置入口、出口、车道、相机、道闸和收费规则；
5. 支持车辆自动识别入场、计费、支付、出场和开闸；
6. 支持岗亭实时查看通行、支付、设备和异常情况；
7. 支持车主通过微信小程序缴费、购买月卡、领取优惠券和补缴欠费；
8. 支持平台统一商户和客户独立商户两种微信支付模式；
9. 支持臻识和信路通相机、道闸首期接入；
10. 支持设备告警、远程控制和失败重试；
11. 支持多租户和多停车场数据隔离；
12. 支持首期约 10 个停车场，并预留扩展至 100 个停车场的能力。

### 2.3 第一阶段核心主链路

第一阶段必须稳定实现：

> 相机识别车辆入场 → 校验设备及车道 → 创建通行记录和停车记录 → 根据规则计算费用 → 车主小程序支付或零元结清 → 支付结果确认 → 出口识别 → 校验放行条件 → 道闸开闸回执 → 生成出场记录 → 完成停车订单。

### 2.4 第一阶段交付边界

第一阶段包含：

- 公有云 SaaS；
- 总后台、运营端、岗亭 Web 端、统一微信小程序；
- 客户审核、多停车场、多员工固定角色；
- 停车场、车道、相机、道闸配置；
- 臻识、信路通设备接入；
- 临时车、月卡车、白名单、黑名单；
- 入场、出场、停车记录、停车订单；
- 多套收费规则及人工切换；
- 微信支付双商户模式；
- 欠费补缴；
- 月卡购买、续费、绑定车辆；
- 停车优惠券；
- 无牌车扫码通行；
- 设备告警和远程控制；
- 经营数据看板；
- 支付成功和月卡到期微信订阅消息；
- 自动退款的特定系统场景；
- 受控试运营和正式商用上线流程。

第一阶段不包含：

- 客户独立微信小程序；
- 客户本地私有化部署；
- Kubernetes；
- 全面微服务化；
- 常规人工停车费退款；
- 电子发票；
- 短信通知；
- 在线投诉、意见反馈和退款异议；
- 停车订单和支付记录 Excel 导出；
- 岗亭现金收费和交接班；
- 预约停车完整业务；
- 共享停车完整业务；
- 大华及其他厂商正式接入；
- 显示屏、语音播报、地感、补光灯正式接入。

上述未实现功能应在数据结构或接口层面保留合理扩展能力，但不得影响第一阶段主链路交付。

## 3. 系统用户与角色

### 3.1 平台超级管理员

使用端：总后台。

权限范围：全平台、全部客户、全部停车场。

主要职责：

- 审核客户注册；
- 启用、禁用和管理客户；
- 管理客户额度、套餐和 SaaS 收费策略；
- 查看和管理所有停车场；
- 查看设备、通行、订单、支付和告警；
- 配置平台级参数、数据保留期限和最大图片保留期限；
- 审核客户独立微信商户关键配置；
- 配置平台统一商户、服务商、分账和结算能力；
- 管理平台账号、固定角色、菜单和权限；
- 进入客户视角进行远程协助；
- 处理客户提交的平台协助事项；
- 查看全平台审计日志和经营看板。

超级管理员切换至客户视角时，必须记录真实操作人、目标客户、目标停车场、操作时间、操作内容和结果，不得伪造成客户本人操作。

### 3.2 平台运营人员

使用端：总后台。

主要职责：

- 查看客户和停车场运营状态；
- 协助客户完成初始化配置；
- 查看设备告警和退款异常；
- 处理客户服务请求；
- 查看平台统计；
- 按授权处理客户资料和业务异常。

平台运营人员不得默认拥有超级管理员全部权限。

### 3.3 客户管理员

使用端：运营端。

权限范围：当前客户名下全部停车场。

主要职责：

- 维护客户和企业资料；
- 创建、修改和管理多个停车场；
- 创建客户员工账号；
- 管理停车场管理员、财务、设备运维和岗亭人员；
- 设置停车场总车位数；
- 配置车道、相机、道闸和收费规则；
- 配置支付主体和支付参数；
- 配置月卡、优惠券、欠费、人工放行和减免规则；
- 查看订单、支付、月卡、欠费和经营数据；
- 处理退款异常任务；
- 停用或重新启用停车场；
- 提交平台协助。

### 3.4 停车场管理员

使用端：运营端。

权限范围：被授权停车场。

主要职责：

- 管理停车场基础信息和总车位数；
- 管理车道、相机和道闸；
- 配置和切换收费规则；
- 管理月卡、白名单、黑名单和优惠券；
- 查看通行、订单、支付和告警；
- 处理停车场异常业务；
- 管理岗亭人员；
- 手动删除抓拍图片并填写原因。

停车场管理员无权停用停车场。

### 3.5 财务人员

使用端：运营端。

固定角色，第一阶段不支持客户自定义权限。

主要职责：

- 查看当前客户授权范围内订单、支付、分账和结算数据；
- 查看退款异常和未退差额；
- 查看 SaaS 服务费和平台抽成数据；
- 不得修改停车场设备和通行配置。

### 3.6 设备运维人员

使用端：运营端。

主要职责：

- 查看设备状态、心跳和告警；
- 处理设备告警；
- 按权限执行远程开闸、关闸、重启和抓拍；
- 查看设备指令日志和回执；
- 不得修改支付、收费和财务数据。

### 3.7 岗亭工作人员

使用端：岗亭 Web 端。

第一阶段职责：

- 查看实时入场、出场和通行记录；
- 查看车牌、原始抓拍图片、停车时长和应收金额；
- 查看订单和支付状态；
- 查看设备在线状态和关键告警；
- 处理无牌车和识别异常；
- 按停车场配置执行人工放行；
- 按权限选择人工放行费用处理方式；
- 按权限提交或执行人工减免；
- 修改或确认识别错误的车牌；
- 查看开闸执行结果。

第一阶段岗亭端不支持：

- 现金收费；
- 交接班；
- 切换收费规则；
- 停用停车场；
- 修改支付配置。

### 3.8 普通车主

使用端：平台统一微信小程序。

主要能力：

- 微信登录和手机号绑定；
- 绑定和管理车牌；
- 自动查询绑定车牌的当前停车记录；
- 查看停车时长、费用和停车场联系方式；
- 使用优惠券；
- 微信支付停车费；
- 查询支付结果；
- 查询停车和缴费记录；
- 欠费补缴；
- 购买、续费和管理月卡；
- 接收缴费成功和月卡到期提醒；
- 无牌车扫码生成临时通行凭证。

第一阶段不允许未绑定车牌直接查询车辆停车记录。

## 4. 多租户、组织与数据权限

### 4.1 租户模型

一个客户对应一个租户。一个租户可以管理多个停车场。

核心业务数据至少包含：

- `tenant_id`：客户或租户标识；
- `parking_lot_id`：停车场标识；
- 必要时包含 `lane_id`、`booth_id`、`device_id`。

### 4.2 第一阶段员工权限模型

第一阶段允许客户创建多个员工账号，但仅提供固定角色：

- 客户管理员；
- 停车场管理员；
- 财务人员；
- 设备运维人员；
- 岗亭人员。

第一阶段不支持客户自定义角色和自定义权限组合。后续可扩展 RBAC 自定义角色。

### 4.3 数据隔离要求

- 平台超级管理员可查看全平台数据；
- 平台运营人员按授权查看数据；
- 客户管理员只能访问本租户数据；
- 停车场管理员和岗亭人员只能访问授权停车场；
- 财务人员只能访问授权财务数据；
- 设备只能上报和操作其绑定停车场、车道的数据；
- 车主只能访问本人绑定车辆及本人关联订单；
- 所有权限必须由后端校验；
- 前端隐藏菜单不能替代后端鉴权；
- 禁止直接信任客户端传入的 `tenant_id` 和 `parking_lot_id`；
- 非法租户、停车场、车道和设备标识必须失败关闭；
- 数据导入、定时任务、消息消费和 WebSocket 推送也必须执行租户隔离。

### 4.4 超级管理员代客户操作

总后台支持超级管理员切换客户视角进入运营端。

要求：

- 页面明确显示“平台代操作”状态；
- 所有写操作必须记录真实平台用户；
- 记录目标客户和停车场；
- 记录操作前和操作后数据；
- 支持按客户、操作人、时间和业务类型查询审计日志。

## 5. 客户注册、审核与 SaaS 商业能力

### 5.1 客户注册流程

1. 客户访问运营端注册页面；
2. 填写企业名称、联系人、手机号等资料；
3. 提交注册申请；
4. 系统创建待审核租户和待审核管理员账号；
5. 总后台人工审核；
6. 审核通过后启用客户；
7. 客户管理员登录运营端；
8. 创建停车场并完成基础配置；
9. 配置关键设备和支付后申请停车场启用。

客户注册后未审核通过前，不允许正式使用运营端业务功能。

### 5.2 客户资源额度

系统支持按客户限制：

- 停车场数量；
- 车道数量；
- 设备数量；
- 员工账号数量；
- 其他可扩展资源。

首批客户由总后台手动配置额度。后续扩展标准套餐、购买、续费和自动扩容。

### 5.3 SaaS 服务费模式

支持组合计费：

- 按月或按年固定服务费；
- 按停车场数量收费；
- 按车道数量收费；
- 按设备数量收费；
- 按员工账号数量收费；
- 按订单数量收费；
- 按停车交易金额抽成；
- 多种模式组合。

总后台可为不同客户配置独立方案。

### 5.4 SaaS 欠费与服务限制

客户未按时支付 SaaS 服务费时，由总后台配置：

- 宽限期；
- 限制开始时间；
- 限制功能范围；
- 是否禁止新增停车场、设备或员工；
- 是否限制后台配置；
- 是否允许车辆入场；
- 是否保留缴费；
- 是否允许车辆出场；
- 是否保留自动开闸；
- 最终停用规则。

系统必须始终保留应急人工放行能力，不得因 SaaS 欠费导致场内车辆无法离场。

## 6. 停车场、区域、车道与车位

### 6.1 停车场基础信息

停车场至少包含：

- 名称；
- 客户；
- 地址；
- 联系电话；
- 经纬度预留；
- 总车位数；
- 当前在场车辆数；
- 当前剩余车位数；
- 状态；
- 支付模式；
- 图片保存期限；
- 业务数据保存期限；
- 缴费后免费离场时间；
- 人工放行策略；
- 离线运行策略；
- 其他停车场级配置。

### 6.2 多停车场

一个客户允许创建和管理多个停车场。停车场之间的：

- 车道；
- 设备；
- 收费规则；
- 订单；
- 支付；
- 月卡；
- 优惠券；
- 欠费；
- 通行记录；
- 经营统计

必须独立隔离。

### 6.3 车道模型

停车场支持多个入口、出口和车道。

车道至少包含：

- 车道名称和编码；
- 入口、出口或混合类型；
- 所属停车场；
- 绑定相机；
- 绑定道闸；
- 当前状态；
- 自动放行策略；
- 是否为关键车道；
- 其他业务参数。

### 6.4 停车场总车位数

客户管理员和停车场管理员均可修改总车位数。

修改必须记录：

- 修改前数值；
- 修改后数值；
- 操作人；
- 操作时间；
- 修改原因。

### 6.5 剩余车位计算

默认公式：

> 剩余车位数 = 总车位数 - 当前有效在场车辆数

系统允许授权人员人工修正剩余车位数。人工修正必须记录修改前后数值、原因、操作人和时间。

后续可接入车位检测器，但不属于第一阶段。

### 6.6 停车场营业状态

第一阶段停车场默认全天营业，不支持按星期、节假日和特殊日期配置营业时段。

支持：

- 启用；
- 停用。

只有总后台和客户管理员可以停用停车场。

停用时，由操作人选择保留范围：

- 是否允许新车入场；
- 是否允许缴费；
- 是否允许出场；
- 是否保留自动开闸；
- 是否仅限制后台配置。

重新启用前必须校验：

- 有效收费规则；
- 入口、出口和车道配置；
- 相机和道闸绑定；
- 关键设备在线；
- 支付配置可用；
- 停车场容量完整。

只要入口相机、出口相机、道闸等关键设备正常，即可启用。非关键设备离线时可启用，但必须显示风险提示。

## 7. 设备接入与设备管理

### 7.1 第一阶段设备范围

第一阶段正式接入：

- 车牌识别相机；
- 道闸。

第一阶段优先厂商：

- 臻识；
- 信路通。

后续扩展：

- 大华及其他厂商；
- 显示屏；
- 语音播报；
- 地感；
- 补光灯；
- 车位检测器；
- 其他停车辅助设备。

### 7.2 接入方式

臻识和信路通的接入方式不预先限定，以具体设备型号、固件和厂商资料为准。

系统需要支持或预留：

- HTTP/HTTPS 回调；
- HTTP OpenAPI；
- TCP Socket；
- MQTT 3.1.1；
- MQTT 5；
- 厂商 Java SDK；
- JNI/JNA；
- Windows DLL；
- Linux SO；
- 后续设备边缘代理。

### 7.3 公网接入模式

首批停车场设备直接通过普通公网 HTTP、TCP 或 MQTT 接入云平台。

第一阶段：

- 不要求专线；
- 不要求固定公网 IP；
- 不强制部署停车场边缘代理。

对于无法直接访问公网或依赖旧版本地 SDK 的设备，后续通过边缘代理兼容。

### 7.4 统一设备适配层

停车核心业务不得直接依赖厂商字段、厂商 SDK 或厂商回调结构。

统一适配层负责：

- 设备注册和身份识别；
- 协议解析；
- 厂商字段转换；
- 统一事件转换；
- 统一指令转换；
- 图片地址或数据处理；
- 设备和停车场归属校验；
- 消息签名校验；
- 时间戳和随机数校验；
- 重放攻击防护；
- 重复消息幂等；
- 心跳处理；
- 在线状态更新；
- 指令下发和回执；
- 失败重试；
- 设备通信日志。

### 7.5 统一设备事件

至少定义：

- 车牌识别事件；
- 入场识别事件；
- 出场识别事件；
- 心跳事件；
- 上线事件；
- 离线事件；
- 开闸结果事件；
- 关闸结果事件；
- 抓拍结果事件；
- 重启结果事件；
- 设备告警事件；
- 离线记录补传事件。

事件至少包含：

- 厂商事件编号；
- 平台事件编号；
- 设备编号；
- 停车场和车道；
- 事件时间；
- 平台接收时间；
- 车牌；
- 车辆类型；
- 图片；
- 原始报文摘要；
- 幂等键；
- 处理状态。

### 7.6 统一设备指令

第一阶段支持：

- 远程开闸；
- 远程关闸；
- 远程重启；
- 远程抓拍。

后续预留：

- 常开；
- 取消常开；
- 同步时间；
- 同步白名单；
- 配置下发；
- 查询设备状态。

### 7.7 远程控制权限与审计

执行设备远程控制前必须校验：

- 操作人权限；
- 租户；
- 停车场；
- 车道；
- 设备归属；
- 设备状态；
- 指令类型是否支持。

必须记录：

- 指令编号；
- 操作人；
- 指令参数；
- 下发时间；
- 重试次数；
- 设备回执；
- 最终结果；
- 关联车辆和订单；
- 操作原因。

### 7.8 指令失败重试

设备远程控制失败后，系统自动按固定次数重试。具体默认次数和间隔由系统参数配置。

超过最大重试次数仍失败时：

- 标记指令失败；
- 生成设备告警；
- 记录完整失败日志；
- 允许授权人员手动重试。

### 7.9 设备在线状态

在线状态由心跳和超时共同判断，不得仅依赖最近一次业务上报。

设备状态至少包括：

- 未激活；
- 在线；
- 离线；
- 故障；
- 禁用；
- 维护中。

### 7.10 设备告警

第一阶段支持：

- 设备离线；
- 心跳超时；
- 开闸失败；
- 关闸失败；
- 重启失败；
- 抓拍失败；
- 设备重复异常；
- 其他可扩展告警。

告警状态：

- 待确认；
- 处理中；
- 已恢复；
- 已关闭。

告警记录：

- 设备；
- 停车场；
- 车道；
- 告警类型；
- 告警时间；
- 最后发生时间；
- 处理人；
- 处理说明；
- 状态历史。

设备恢复在线后，系统自动将对应离线告警标记为已恢复并自动关闭，同时保留完整历史。

第一阶段告警仅在总后台和运营端展示，不发送微信、短信或邮件。

### 7.11 离线能力

停车场离线运行能力由停车场根据设备能力配置：

- 仅在线运行；
- 设备本地基本通行，恢复网络后补传；
- 完整离线识别、计费和放行。

第一阶段云平台提供配置、同步、幂等和补传接口。完整离线能力是否可用，取决于具体厂商设备或后续边缘代理能力。

## 8. 车辆、车牌与车主绑定

### 8.1 车辆类型

系统预留：

- 小型车；
- 大型车；
- 新能源车；
- 其他车辆类型。

停车场可自行配置是否启用车型差异化收费。

### 8.2 车主绑定车牌

车主在小程序绑定车牌后，系统自动匹配该车牌当前有效在场记录。

不支持未绑定车牌直接查询停车记录。

### 8.3 车牌绑定验证

验证强度由停车场配置，可选择：

- 仅输入车牌；
- 手机号验证；
- 上传行驶证或车辆证明；
- 人工审核；
- 其他扩展验证。

### 8.4 同一车牌多账号绑定

由停车场配置：

- 单一微信账号绑定；
- 主车主授权其他账号绑定；
- 允许多个账号直接绑定。

无论采用哪种模式，都必须防止越权查询和非法支付后查看敏感记录。

### 8.5 无牌车

第一阶段支持无牌车扫码通行。

基本流程：

1. 车主扫描停车场或入口二维码；
2. 小程序生成临时通行凭证；
3. 凭证关联停车场、入口、时间和用户；
4. 系统创建无牌车入场记录；
5. 停车期间凭证用于查询和缴费；
6. 出场时通过二维码或岗亭确认关联订单；
7. 完成开闸和出场记录。

临时凭证必须防伪造、防重复使用并具备有效期。

## 9. 车辆入场、停车与出场

### 9.1 入场流程

1. 入口相机识别车辆；
2. 相机上报设备编号、车牌、时间和原图；
3. 设备适配层完成鉴权和协议解析；
4. 校验设备、停车场和车道绑定；
5. 校验消息签名、时间戳和幂等键；
6. 判断车辆类型和特殊车辆身份；
7. 处理重复入场策略；
8. 创建入场通行记录；
9. 创建停车记录；
10. 更新当前在场车辆数和剩余车位；
11. 向岗亭端推送实时事件；
12. 根据停车场策略决定是否下发开闸；
13. 保存开闸指令和回执。

### 9.2 同车多条未完成停车记录

由停车场配置：

- 严格限制同车同停车场仅一条未完成记录；
- 允许异常情况下存在多条；
- 允许管理员合并、作废或指定有效记录。

### 9.3 重复入场策略

由停车场配置：

- 拒绝创建新记录；
- 自动关闭上一条记录后创建新记录；
- 合并记录；
- 转人工处理。

所有自动处理和人工处理必须记录日志。

### 9.4 车辆在场状态

停车记录至少包含：

- 入场时间；
- 当前状态；
- 入场停车场和车道；
- 入场设备；
- 入场原图；
- 车辆类型；
- 当前收费规则版本；
- 当前应付金额；
- 是否已支付；
- 是否存在欠费；
- 是否存在异常。

### 9.5 出场匹配

出口相机识别后，系统匹配有效未完成停车记录。

车牌不完全一致时，由停车场配置：

- 匹配算法；
- 相似度阈值；
- 是否允许自动放行；
- 低于阈值时是否转岗亭确认。

### 9.6 缴费后放行策略

车主缴费成功后的放行方式由停车场配置，可按车道、时间段或车辆类型设置：

- 支付成功立即开闸；
- 仅更新已支付状态，车辆到达出口识别后开闸；
- 岗亭确认后开闸。

推荐默认：出口识别后开闸。

### 9.7 已缴费但出口识别失败

由停车场配置应急方式：

- 岗亭人工核验；
- 小程序扫码关联已支付订单；
- 同时启用多种方式。

### 9.8 订单完成条件

停车订单只有同时满足以下条件后才能标记为完成：

1. 收到道闸开闸成功回执；
2. 成功生成出场记录。

若未收到回执或出场记录创建失败：

- 不得直接完成订单；
- 订单进入异常或待补偿状态；
- 启动自动补偿；
- 允许人工处理。

### 9.9 出场流程

1. 出口相机识别车辆；
2. 匹配停车记录；
3. 校验停车场和车道；
4. 计算或确认应付金额；
5. 检查月卡、白名单、优惠券、支付和欠费；
6. 判断是否满足放行；
7. 下发开闸指令；
8. 接收开闸成功回执；
9. 创建出场记录；
10. 更新停车记录；
11. 更新车位数量；
12. 完成订单；
13. 推送岗亭端。

## 10. 收费规则与计费

### 10.1 收费规则能力

至少支持：

- 免费时长；
- 按小时收费；
- 按半小时或自定义计费单位；
- 首时段收费；
- 后续时段收费；
- 单日封顶；
- 跨天计费；
- 分时段收费；
- 白天和夜间差异收费；
- 固定金额收费；
- 临时车、月卡车、白名单车差异；
- 车型差异化收费；
- 人工减免；
- 优惠券抵扣；
- 缴费后超时再次计费。

### 10.2 日期差异化收费

停车场可配置是否启用：

- 工作日；
- 周末；
- 法定节假日；
- 指定特殊日期。

第一阶段允许配置能力，但收费规则自动匹配范围受第 10.4 节限制。

### 10.3 多套收费规则

第一阶段允许一个停车场配置多套收费规则。

第一阶段不实现按车型、时间或入口自动匹配多套规则。当前生效规则由客户管理员或停车场管理员手动选择。

### 10.4 收费规则切换权限

仅以下角色可以切换：

- 客户管理员；
- 停车场管理员。

岗亭人员无权切换收费规则。

切换必须记录：

- 原规则；
- 新规则；
- 操作人；
- 操作时间；
- 操作原因；
- 生效范围。

### 10.5 对已在场车辆的影响

切换规则时，由操作人选择：

- 仅对新入场车辆生效；
- 对当前未完成停车记录同时生效。

若影响已在场车辆，必须记录重新计费结果。

### 10.6 已缴费未出场车辆

收费规则切换影响已缴费但尚未出场车辆时，由操作人选择：

- 保持原缴费结果；
- 按新规则重新计费并补差额；
- 仅计算规则切换后的新增停车时长；
- 其他授权处理方式。

必须记录原规则、新规则、原支付金额、新计费金额、处理人和原因。

### 10.7 缴费后免费离场时间

由停车场配置。车辆缴费成功后，在免费离场时间内出场不产生新增费用。

超过免费离场时间后，重新计费方式由停车场配置：

- 仅收取超过免费离场时间后的新增费用；
- 从缴费完成时间重新计费；
- 重新计算整笔订单并扣除已支付金额。

### 10.8 计费安全

- 金额使用高精度十进制类型；
- 禁止使用浮点数直接计算；
- 应付金额不得小于 0；
- 应付金额为 0 时直接结清；
- 每次计费保存规则版本和计费明细；
- 历史订单不得因规则修改失去可追溯性；
- 同一输入和规则版本必须得到确定性结果。

### 10.9 收费规则版本

收费规则必须具备版本化：

- 规则 ID；
- 版本号；
- 生效时间；
- 失效时间；
- 创建人；
- 修改人；
- 规则快照；
- 当前是否启用。

- 减免额度；
- 预设原因；
- 单笔和累计限制。

- 原应付金额；
- 减免金额；
- 减免后金额；

- 操作人；
- 审批人；

- 人工减免；
- 异常订单处理。

## 12. 停车订单

### 12.1 订单生成

- 原始金额；
- 优惠金额；
- 应付金额；

- 支付主体；
- 状态；
- 创建、支付、完成时间；
- 异常状态和原因。

## 13. 微信支付、多商户与分账结算

### 13.1 第一阶段支付模式

第一阶段同时支持：

1. 平台统一商户号；
2. 客户独立商户号。

不同停车场可以选择不同支付模式。

### 13.2 平台统一商户模式

平台统一收款时，使用微信支付服务商、分账或电商收付通等能力实现自动结算。

系统需要记录：

- 实际收款主体；
- 客户；
- 停车场；
- 总金额；
- 微信手续费；
- 平台服务费；
- 平台抽成；
- 客户应结算金额；
- 分账状态；
- 结算状态；
- 退款对分账的影响。

### 13.3 客户独立商户模式

客户可在运营端自行填写支付配置，也可由总后台协助配置。

关键参数必须由总后台审核后才能启用，包括：

- 商户号；
- 应用标识；
- 商户证书；
- API 密钥；
- 回调配置；
- 其他敏感参数。

敏感参数必须加密存储和脱敏展示。

### 13.4 支付流程

1. 车主查询订单；
2. 系统校验订单、停车场和支付主体；
3. 应用优惠券；
4. 应付金额大于 0 时创建支付单；
5. 调用对应微信商户下单；
6. 小程序发起支付；
7. 服务端接收微信支付回调；
8. 校验签名、商户号、应用标识、订单号、金额、币种和状态；
9. 幂等更新支付单；
10. 更新停车订单；
11. 创建放行任务；
12. 推送岗亭端。

小程序前端返回“支付成功”不得作为最终支付依据。最终状态以微信服务端回调或后端主动查询为准。

### 13.5 零元订单

优惠券或其他减免将应付金额抵扣至 0 时：

- 不调用微信支付；
- 订单直接标记为已结清；
- 记录零元结清原因和优惠明细；
- 按停车场放行策略处理。

### 13.6 支付单

支付单至少包含：

- 平台支付单号；
- 停车订单号；
- 收款模式；
- 商户号；
- 应用标识；
- 支付金额；
- 支付渠道；
- 第三方交易号；
- 支付状态；
- 创建时间；
- 支付时间；
- 回调摘要；
- 对账状态；
- 退款状态。

### 13.7 支付幂等

必须防止：

- 同一订单重复下单；
- 重复支付；
- 重复支付回调；
- 错误金额回调；
- 不同商户订单串单；
- 已关闭订单被再次支付。

## 14. 自动退款与退款异常

### 14.1 第一阶段退款边界

第一阶段不开放普通人工停车费退款流程。

第一阶段支持系统场景自动退款，例如：

- 收费规则切换导致应退金额；
- 重复支付；
- 金额异常；
- 其他系统确认的自动退款场景。

月卡退款由月卡类型配置，但具体完整运营流程可分阶段启用。

### 14.2 收费规则切换退款

车辆已缴费但未出场，重新计费产生应退金额时，系统自动按原支付渠道退款。

记录：

- 原停车订单；
- 原支付单；
- 原规则和新规则；
- 原支付金额；
- 新计费金额；
- 系统应退金额；
- 第三方退款单号；
- 退款状态；
- 操作人和原因。

### 14.3 自动退款失败

自动退款失败后：

1. 按固定次数自动重试；
2. 记录每次请求时间和第三方错误；
3. 超过次数仍失败时生成退款异常任务和告警；
4. 在总后台和对应客户运营端展示。

### 14.4 退款异常任务处理人

由客户管理员优先处理，必要时提交总后台协助。

### 14.5 客户管理员可执行操作

- 查看失败原因；
- 重新发起退款；
- 修改退款金额；
- 提交总后台协助。

退款未成功前，不允许直接关闭异常任务。

### 14.6 修改退款金额

无需额外审批，但必须满足：

- 不得超过系统重新计费计算的应退金额；
- 不得超过原支付金额减累计已退款金额；
- 只能减少，不能增加；
- 必须填写调整原因。

### 14.7 未退差额

退款金额调低后，剩余部分生成未退差额记录。

记录：

- 系统应退金额；
- 实际线上退款金额；
- 未退差额；
- 差额处理方式；
- 内部处理说明；
- 操作人；
- 处理时间。

客户管理员填写完整处理说明后，可标记未退差额处理完成，不强制上传补偿凭证或要求车主确认。

车主小程序仅展示实际退款金额，不展示内部处理说明。

### 14.8 车主退款沟通

第一阶段不提供线上退款异议流程。小程序展示停车场客服电话和联系方式，车主通过线下方式沟通。

## 17. 优惠券

### 17.1 第一阶段券类型

- 平台券：总后台创建，可跨客户或停车场使用；
- 客户券：客户管理员创建，仅限当前客户；
- 停车场券：停车场管理员创建，仅限指定停车场。

### 17.2 优惠形式

至少支持：

- 固定金额减免；
- 固定停车时长减免；
- 满减；
- 其他可扩展类型。

### 17.3 规则字段

- 券名称；
- 券类型；
- 发行主体；
- 适用客户和停车场；
- 适用车辆类型；
- 使用门槛；
- 优惠金额或时长；
- 有效期；
- 发放总量；
- 单用户限领；
- 是否可叠加；
- 可叠加券类型；
- 最大叠加数量；
- 互斥关系；
- 发放状态。

### 17.4 获取方式

第一阶段支持：

- 车主主动领取；
- 平台、客户或停车场定向发放；
- 支付成功、月卡购买或运营活动自动发放。

### 17.5 优惠券组合

同一订单是否叠加由券规则配置。

系统自动计算优惠金额最大的合法组合，综合考虑：

- 适用条件；
- 有效期；
- 使用门槛；
- 互斥关系；
- 可叠加类型；
- 最大叠加数量；
- 最终优惠金额。

默认规则：系统自动应用最优组合，车主可取消全部优惠，但第一阶段不提供复杂的手动重新组合能力。

### 17.6 零元抵扣

优惠券允许将订单抵扣至 0 元，直接结清并按放行策略处理。

### 17.7 券使用幂等

必须防止：

- 同一券重复使用；
- 并发订单重复锁券；
- 支付失败后券状态无法恢复；
- 订单关闭后券未退回；
- 跨租户或跨停车场非法使用。

## 23. 图片、文件与数据保留

## 32. 接口与编码规范

### 32.1 接口原则

- REST 风格；
- 统一返回结构；
- 统一错误码；
- 分页参数统一；
- 时间统一使用明确时区；
- 金额接口明确单位；
- 敏感字段脱敏；
- 写接口支持幂等键；
- 设备接口与业务接口分离；
- 支付回调接口独立安全策略。

### 32.2 模块协作

- Controller → Application Service → Domain/Service → Repository/Mapper；
- 禁止 Controller 直接写复杂查询和状态更新；
- 禁止设备适配器直接修改支付订单；
- 禁止支付模块直接调用厂商 SDK；
- 模块间通过公开接口或事件协作。

### 32.3 数据库变更

- 使用 Flyway；
- 每次变更生成独立迁移脚本；
- 禁止直接修改已发布迁移；
- 生产迁移前备份；
- 核心表增加必要索引；
- 所有租户表考虑 `tenant_id`、`parking_lot_id` 联合索引。

- 每日核对订单、支付和出场；
- 观察设备在线率和开闸成功率。

### 35.3 阶段三：正式商用

主链路、设备、支付、数据隔离、备份和应急机制全部通过验收后，全面开放。

## 36. 第一阶段验收标准

### 36.1 基础配置

- 一个客户可创建多个停车场；
- 可创建固定角色员工；

- 识别上报稳定；
- 远程开闸、关闸、抓拍和重启可用；
- 失败重试和告警可用；

- 收到开闸回执并生成出场记录后完成订单；
- 未支付车辆不得自动放行；

### 36.4 多商户支付

- 客户独立商户模式通过；
- 关键参数审核有效；
- 支付回调验签和金额校验通过；
- 分账或结算数据可追踪；
- 自动退款和失败重试通过。

### 36.5 月卡和欠费

### 36.6 数据和安全

- 多租户隔离测试通过；
- 停车场数据范围测试通过；
- 支付和设备接口安全测试通过；
- 高风险操作审计完整；
- 图片权限正确；
- 数据备份和恢复演练通过。

### 36.7 稳定性

- 真实设备连续运行 24 至 72 小时；
- 无严重数据丢失；
- 重复消息不产生重复订单；
- 支付成功不因消息丢失导致永久无法放行；
- 关键异常可以补偿和人工处理。

## 37. 上线前禁止项

出现以下任一情况，不得全面正式商用：

- 多停车场数据隔离未通过；
- 支付回调验签或金额校验不完整；
- 支付成功后可能永久无法开闸且无补偿；
- 设备心跳和在线状态不准确；
- 车辆重复识别会生成重复有效订单；
- 开闸无审计或可跨停车场调用；
- 数据库无备份和恢复方案；
- 岗亭无人工应急放行；
- 臻识或信路通真机联调未完成；
- 核心主链路未经过真实环境连续测试。

## 39. 最终确认结论

本项目第一阶段采用：

> Java 21 LTS + Spring Boot 3.5.x + 模块化单体 + Sa-Token + Redis + MyBatis-Plus + MySQL 8.4 LTS + Flyway + RabbitMQ + EMQX + WebSocket + Vue 3 + TypeScript + Arco Design Vue + 原生微信小程序 + 云对象存储 + Docker Compose + Nginx。

第一阶段以公有云 SaaS 形式交付，按约 10 个停车场实际接入规模设计，并为 100 个停车场保留架构冗余。

首期优先接入臻识和信路通车牌识别相机、道闸，设备直接通过普通公网接入云平台。所有厂商设备通过统一设备适配层接入，停车核心业务不直接依赖厂商协议。

系统同时支持平台统一微信商户和客户独立微信商户。平台统一商户模式支持服务商、分账或电商收付通等自动结算能力。

上线采用“受控试运营 → 小范围正式收费 → 全面商用”的分阶段策略。只有在设备真机、支付安全、多租户隔离、主链路稳定、异常补偿和备份恢复全部通过后，才能全面正式运营。
