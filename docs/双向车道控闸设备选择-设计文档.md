## 一、背景与问题

### 1.1 问题症状

双向车道（`parking_lane.type=3`）手动开/关闸时，**不明确开闸信号发到了哪一台相机**。

### 1.2 根因分析

当前 `RecognitionEventServiceImpl` 与 `DeviceService`（L1055 起）的**两处重复解析**均只接收 `laneId`，目标设备解析顺序：

1. 车道上**第一台** `GATE` 设备（多台时任意取）
2. 否则车道上**第一台**带 `OPEN_GATE` 能力的 `CAMERA`（多台时任意取）
3. 否则**回退整个停车场**任意 CAMERA+OPEN_GATE ⚠️

双向车道配有两台相机（`recognition_direction` 分别为 1=ENTRY / 2=EXIT），**两台都带 `OPEN_GATE` 能力**，但闸线只接其中一台。第 2 步任意取首台 → 可能选中未接线的相机 → **开闸指令发出、物理闸不动**（臻识 C5H GPIO 场景）/ 或指令到达错误的设备。

### 1.3 加剧因素：能力标记的信任危机

```java
// DeviceService.java L113
private static final String DEFAULT_CAMERA_CAPABILITIES = "OPEN_GATE";

// L251
device.setCapabilities(defaultString(request.getCapabilities(),
    "CAMERA".equals(deviceType) ? DEFAULT_CAMERA_CAPABILITIES : DEFAULT_CAPABILITIES));
```

- **任何 CAMERA 创建时，不显式指定能力即默认带 `OPEN_GATE`**
- capabilities 挂在设备**实例**，`device_model` / `device_vendor` 表无能力字段
- `device_model` 无型号能力字段，无法表达"芊熠 Q3 = 无 IO 关闸 / 臻识 C5H = 有 GPIO 控闸"
- 芊熠型号种子仅 `QY-01` 占位（V20260905001）

### 1.4 已核实现场事实

| 事实 | 来源 |
|---|---|
| **物理形态 = 单闸共用**：双向车道仅一台道闸，闸线只接一台设备 | 用户确认 |
| **芊熠 Q3 = 可开闸、不可关闸**：开闸走 Q3 自身继电器，关闸纯靠地感触发 | 用户确认 |
| **能力是型号级属性**：Q3 的 IO 控闸限制是型号硬件特性，非车道配置问题 | 用户确认 |
| `parking_lane.type`、`device.recognition_direction`、`device.camera_role`、`gate_mode` 已存在但未被手动链路利用 | 代码审计 |
| 自动开闸链路（`handleEvent` → `findGateDevice`）共用同一解析，存在同样隐患 | 代码审计 |
| device-access 芊熠适配器已支持 `iooutput`（开闸）、`barrierKeepOpen`（常开）；Q3 常开待现场确认 | 代码审计 |

## 二、方案设计

### 2.1 控闸设备建模：车道级 gate_device_id

**`parking_lane` 表新增字段 `gate_device_id`（BIGINT, NULLABLE）**，指向该车道唯一控闸设备（`device.id`）。

| 场景 | gate_device_id 值 |
|---|---|
| 臻识 C5H GPIO 控闸（闸线接相机 A） | 相机 A 的 device.id |
| 芊熠 Q3 车道（闸线接其中一台 Q3） | 接线那台 Q3 的 device.id |
| 独立 GATE 设备（道闸控制器/IO 板） | GATE 设备的 device.id |
| 未配置（存量车道待人工补录） | NULL → 走回退解析 + 触发告警 |

**设计约束**：
- `gate_device_id` 指向的 `device` 必须绑在同一条车道（`device.lane_id = parking_lane.id`）
- 若指向相机，该相机（的型号）必须具有 `OPEN_GATE` 能力
- 校验逻辑见 §2.3.4

### 2.2 设备解析逻辑收敛

#### 2.2.1 共享方法

将 `RecognitionEventServiceImpl` 和 `DeviceService` 中**两处重复的三段式解析**收敛为**单一共享方法**：

```java
// DeviceService.java（新增）
/**
 * 按车道解析控闸设备，优先级：
 *   1. parking_lane.gate_device_id（显式指定，单一事实源）
 *   2. 本车道 GATE 类型设备（唯一候选取之；多候选 → 报错 + 告警）
 *   3. 本车道 CAMERA 含 OPEN_GATE 能力（唯一候选取之；多候选 → 报错 + 告警）
 *   4. 以上皆无 → BusinessException + 告警（已删除停车场级回退）
 *
 * @param laneId 车道 ID
 * @return 控闸设备，绝不返回 null（失败抛异常）
 * @throws BusinessException 未找到或存在多个候选时抛
 */
public Device resolveGateDevice(Long laneId)
```

#### 2.2.2 解析优先级

```
┌─────────────────────────────────┐
│ parking_lane.gate_device_id != NULL?                │
│   └─ YES → 返回该 device（校验 lane_id 一致）        │
│   └─ NO  → 继续                                     │
├─────────────────────────────────┤
│ 本车道(lane_id) GATE 设备（enabled）                 │
│   └─ 0 条 → 继续                                    │
│   └─ 1 条 → 返回                                    │
│   └─ ≥2 条 → 多候选报错（AMBIGUOUS_GATE_DEVICE）     │
├─────────────────────────────────┤
│ 本车道 CAMERA + capabilities 含 OPEN_GATE（enabled）  │
│   └─ 0 条 → 报错（GATE_DEVICE_NOT_FOUND）+ 告警     │
│   └─ 1 条 → 返回                                    │
│   └─ ≥2 条 → 多候选报错（AMBIGUOUS_GATE_DEVICE）     │
├─────────────────────────────────┤
│ ~~停车场级回退~~ 已删除                               │
│   车道级解析失败直接报错 + 产生告警，倒逼台账补全      │
└─────────────────────────────────┘
```

#### 2.2.3 全链路替换清单

以下所有调用点统一替换为 `resolveGateDevice(laneId)`：

| 调用点 | 当前逻辑 | 文件 |
|---|---|---|
| `manualOpenGate(laneId, ...)` | self-contained 三段式 | `RecognitionEventServiceImpl` |
| `manualCloseGate(laneId, ...)` | self-contained 三段式 | `RecognitionEventServiceImpl` |
| `manualLockGate(laneId, ...)` | self-contained 三段式 | `RecognitionEventServiceImpl` |
| `manualUnlockGate(laneId, ...)` | self-contained 三段式 | `RecognitionEventServiceImpl` |
| `manualOpenGateBatch` | 同上 | `RecognitionEventServiceImpl` |
| `findGateDevice(laneId)` (auto open in `handleEvent`) | `selectList l.eq(laneId).eq(GATE) LIMIT1` | `RecognitionEventServiceImpl` L948 |
| `DeviceService.openGate(deviceId)` → 车道级入口 | GATE → CAMERA(OPEN_GATE) → lot fallback | `DeviceService` L1055 |
| `DeviceService.closeGate(deviceId)` | 同上 | `DeviceService` |
| `RemoteGateController` | 按 laneId 解析（待核实接口签名） | `com.jushan.system.controller` |
| `InternalGateController` | 按 laneId 解析（待核实） | `com.jushan.system.controller` |

**对外接口签名不变**：前端 / remote 调用仍传 `laneId`，后端内部按新解析找对设备。`DeviceService.openGate/closeGate` 保留按 `deviceId` 调用的重载供其他链路使用。

### 2.3 型号级能力体系

#### 2.3.1 数据模型

`device_model` 表新增 `capabilities` 字段：

```sql
ALTER TABLE device_model
    ADD COLUMN capabilities VARCHAR(500) DEFAULT NULL
    COMMENT '型号默认能力列表，逗号分隔（如 OPEN_GATE,CLOSE_GATE,CAPTURE）：实例默认继承型号，可覆盖';
```

#### 2.3.2 型号种子

| 型号 | capabilities | 说明 |
|---|---|---|
| 芊熠 Q3（新建/替换 QY-01） | `OPEN_GATE,CAPTURE` | 可开闸 + 可抓拍；不可关闸；不可常开（待现场确认后考虑加 `KEEP_OPEN`） |
| 臻识 C5H（新建/待核实型号 code） | `OPEN_GATE,CLOSE_GATE,CAPTURE` | GPIO 控闸（可开可关）+ 可抓拍；常开待确认 |
| 信路通（待核实） | 按实际硬件能力配置 | — |
| 显示屏 OLM-M1D | `TEXT_DISPLAY`（或其他现有枚举） | — |

#### 2.3.3 实例继承规则

创建/编辑 `Device` 时：
1. 若未显式指定 `capabilities` → 继承 `device_model.capabilities`（型号默认）
2. 若显式指定 → 使用指定值（允许按实例覆盖，如现场未接线可手动去掉 `OPEN_GATE`）
3. **废弃** `DeviceService.DEFAULT_CAMERA_CAPABILITIES = "OPEN_GATE"`；改为继承型号默认

#### 2.3.4 保存校验

保存 `Device`（创建/更新）时校验：

| 校验 | 规则 | 级别 |
|---|---|---|
| 实例能力 ⊆ 型号能力 | `device.capabilities` 每条必须在 `device_model.capabilities` 中存在 | **硬拒绝**（BusinessException） |
| 双向车道 CAMERA 缺 `recognition_direction` | `parking_lane.type=3` 且 `device.device_type=CAMERA` 时 `recognition_direction` 不得为 NULL | **硬拒绝** |
| `gate_device_id` 一致性 | 保存 lane 时校验 `gate_device_id` 指向的 device 的 `lane_id == 本条 lane.id` | **硬拒绝** |
| 同一车道多台 CAMERA 带 `OPEN_GATE` 但无 `gate_device_id` | 保存时 WARN 日志（不做硬拒绝，因为后续保存 gate_device_id 即可解决） | **告警** |

### 2.4 前端按钮：能力驱动渲染

#### 2.4.1 渲染逻辑

岗亭端车道卡片按钮集合 = `resolveGateDevice(laneId)` 返回的设备**型号能力**（`device_model.capabilities`）决定：

| 型号能力 | 岗亭端按钮 | 运营端 gate_mode 选项 |
|---|---|---|
| `OPEN_GATE` | **开闸** | AUTO |
| `CLOSE_GATE` | 开闸 + **关闸** | AUTO |
| `KEEP_OPEN` | 开闸 + 关闸 + **常开 / 取消常开** | AUTO, ALWAYS_OPEN, ALWAYS_CLOSE |
| 无以上 | 无闸控按钮 | ALWAYS_CLOSE?（待核实） |

#### 2.4.2 Q3 按钮集合（当前）

芊熠 Q3 能力 = `OPEN_GATE,CAPTURE` → 岗亭端仅展示「**开闸**」按钮，「关闸」「常开」「取消常开」不渲染。

**常开按钮**：Q3 硬件是否支持 `barrierKeepOpen` 待现场确认。确认前**型号不配 `KEEP_OPEN`**，按钮不展示；确认后改型号种子即可，前端无需改动。

#### 2.4.3 按钮能力查询接口（新增或扩展现有）

```
GET /api/v1/admin/lanes/{laneId}/gate-capabilities
→ R<LaneGateCapabilityVO> {
    gateDeviceId: Long,
    gateDeviceName: String,
    capabilities: ["OPEN_GATE"]  // 控闸设备的能力列表
}
```

前端渲染按钮前调用此接口，按返回的能力列表动态显示/隐藏对应操作按钮。

### 3.3 存量数据补录（随迁移执行，部分需人工介入）

```sql
-- ① 存量芊熠相机能力纠错：去掉 CLOSE_GATE 和 KEEP_OPEN（型号 qy-Q3 无此能力）
UPDATE device d
    INNER JOIN device_model m ON d.model_id = m.id
SET d.capabilities = 'OPEN_GATE,CAPTURE'
WHERE m.code = 'QY-Q3'
  AND d.capabilities IS NOT NULL;

-- ② 存量相机能力继承补漏：未设 capabilities 的相机从型号默认填充
UPDATE device d
    INNER JOIN device_model m ON d.model_id = m.id
SET d.capabilities = m.capabilities
WHERE d.device_type = 'CAMERA'
  AND d.capabilities IS NULL
  AND m.capabilities IS NOT NULL;

-- ③ 双向车道 direction 未补录清单（人工审核后逐条 SQL）
-- 输出待处理清单：
SELECT d.id AS device_id, d.name, d.device_sn, l.id AS lane_id, l.name, l.type
FROM device d
    INNER JOIN parking_lane l ON d.lane_id = l.id AND l.type = 3
WHERE d.recognition_direction IS NULL;

-- ④ gate_device_id 补录：人工逐车道指定接线设备（无脚本自动化，靠台账维护）
-- 补录期间：未配置的车道解析失败将报 GATE_DEVICE_NOT_FOUND + 告警，倒逼补全
```

### 5.1 自动化测试

#### 解析优先级（`resolveGateDevice` 单测）

| TC-3 | GATE=NULL → 走 CAMERA(OPEN_GATE) | NULL | 0 | 1 台 | **返回该相机** |
| TC-4 | GATE=NULL, CAMERA 0 候选 | NULL | 0 | 0 | **抛 GATE_DEVICE_NOT_FOUND + 告警** |
| TC-5 | GATE 多候选（≥2 enabled） | NULL | 2 台 | — | **抛 AMBIGUOUS_GATE_DEVICE + 告警** |
| TC-6 | CAMERA(OPEN_GATE) 多候选 | NULL | 0 | 2 台 | **抛 AMBIGUOUS_GATE_DEVICE + 告警** |
| TC-7 | 双向车道 gate_device_id 指向 entry 相机 | 有（entry 相机） | 0 | entry(有能力)+exit(有能力) | **返回 entry 相机，不返回 exit** |

#### 能力继承与校验

| TC# | 场景 | 预期 |
|---|---|---|
| TC-9 | 创建 Camera 未指定 capabilities → 继承型号默认（Q3=`OPEN_GATE,CAPTURE`） | 实例.capabilities = 型号.capabilities |
| TC-10 | 创建 Camera 指定 capabilities（`OPEN_GATE` only）→ 使用指定值 | 实例.capabilities = 指定值 |

| TC-12 | 保存 gate_device_id 指向 device.lane_id ≠ 当前 lane.id → 抛校验异常 | **硬拒绝** |

### 5.2 人工验收（逐车道，推荐全量覆盖）

#### 验收流程（每条车道）

1. 确认 `parking_lane.gate_device_id` 已填写正确的接线设备
2. 确认 `device_model.capabilities` 与硬件能力一致
3. 确认 `device.capabilities` 与型号一致（或合理覆盖）
4. 岗亭端打开该车道卡片，**检查按钮集合**（Q3=只开闸；C5H=开/关/常开...）
5. **试点开闸**：点击开闸按钮 → 查看 `device_command_audit` 表最新记录
   - `command_type='OPEN_GATE'`
   - `device_sn` == `gate_device_id` 指向设备的 SN
   - 物理闸实际抬起
6. 试点关闸/常开/取消常开（仅能力支持的型号）→ 同步骤 5 核对
7. **负向验证**：故意把 `gate_device_id` 设为 NULL → 预期开闸失败 + 产生告警记录
