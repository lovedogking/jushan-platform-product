# 智慧停车 SaaS 平台 Claude Code 逐任务开发计划

> 适用范围：停车业务平台侧  
> 依据：平台侧需求规格说明书 V1.0、AGENTS.md、CLAUDE.md
> 生成日期：2026-07-10  
> 最后更新：2026-07-11
> 使用方式：一次只执行一个任务；Claude Code 完成并验证后，由 Codex/人工复核，通过阶段闸门后再进入下一任务。
>
> **注意**：原 "停车业务平台与 Device Access 接口规范 V1.0-MERGED" 已归档为 HISTORICAL_V0_1_DESCRIPTION。
> 当前 Device Access 接口事实以共享契约 `docs/contracts/platform-device-access/04-当前兼容契约-v0.2.md` 为准。

## 1. 核心结论

1. 第一阶段采用模块化单体，后端使用 Java 21、Spring Boot 3.5.x、Maven 多模块、MySQL 8.4、MyBatis-Plus、Flyway、Redis、Sa-Token、RabbitMQ、WebSocket、Docker Compose 和 Nginx。
2. 前端推荐 `admin-web + booth-web + miniapp`：
   - `admin-web` 统一承载平台总后台和停车场运营端，通过角色、路由和后端数据范围隔离；
   - `booth-web` 独立部署，降低岗亭实时页面和高风险开闸操作对管理端的影响；
   - `miniapp` 使用原生微信小程序。
3. **SUPERSEDED_BY_SHARED_CONTRACT**：以下旧 v0.1 三接口假设已失效。
   旧假设（不再有效）：
   - ~~`POST /api/v1/devices/{deviceSn}/gate/open`~~（v0.2 中为 NOT_IMPLEMENTED）
   - `POST /api/v1/devices/{deviceSn}/time/sync`（v0.2 中保留）
   - `GET /api/v1/devices/{deviceSn}/status`（v0.2 中保留）
   **Device Access v0.2 当前事实**：7 个 HTTP 端点（设备 CRUD 5 + 校时 + 状态查询）。
   **没有 gate/open**。开闸为 INTENTIONALLY_OUT_OF_SCOPE_IN_V0.2。
   后续跨系统阶段必须根据共享契约重新拆分。详见 `docs/contracts/platform-device-access/`。
4. 开闸无 `commandId` 幂等，每次调用都可能产生真实动作。任何网络错误或读取超时必须进入 `UNCERTAIN`，不得自动重试。
5. 当前没有冻结的车牌识别事件、图片上传/补传、HMAC、关闸、抓拍、重启或信路通真实接口。自动真机入场必须等待正式契约；在此之前只能使用生产禁用的 Mock/人工触发验证平台业务。
6. 四周受控试运营和完整第一阶段不是同一个目标。受控试运营以单停车场、一进一出、臻识 C5H、测试车辆、人工兜底为边界；完整第一阶段还包括双商户、月卡、优惠券、欠费、无牌车、信路通、退款、看板和正式设备事件。

## 2. 两条开发路线

### 2.1 四周受控试运营关键路径

优先完成：T01–T39、T40–T41、T47–T52。

- 没有微信支付资料时：使用零元订单或明确标记的支付 Mock 验证平台状态机，不向真实车主收费。
- 没有车牌识别事件契约时：使用仅 local/test 可用的 Mock/人工触发入口，不得宣称真机自动入场闭环。
- 进入真实收费前：必须追加完成 T42–T46，并通过支付安全测试。
- 受控试运营不以月卡、优惠券、SaaS 商业计费、信路通和完整看板为前置条件。

### 2.2 完整第一阶段产品路线

在 T52 后继续完成 T53–T62。完整一期只有在臻识和信路通真机、双支付主体、主链路、安全隔离、备份恢复和连续稳定性全部通过后，才能正式商用。

### 二、开始修改前的强制检查

首先执行并记录：

```bash
git status --short
git branch --show-current
git rev-parse --short HEAD
```

随后完成以下检查：

1. 检查用户未提交改动、未跟踪文件和当前分支。
2. 阅读当前任务涉及的源码、测试、迁移、配置和真实调用链。
3. 确认当前任务的前置依赖是否已经完成。
4. 确认任务卡中的文件路径、模块名称、接口和命令是否与真实仓库一致。
5. 确认是否存在可以复用的现有实现，禁止无条件重写。
6. 确认本任务是否需要数据库迁移、接口变更、配置变更或外部依赖。

在修改任何文件前，先输出：

1. 当前任务目标。
2. 前置依赖检查结果。
3. 允许修改范围。
4. 禁止修改范围。
5. 预计修改文件或模块。
6. 实施步骤。
7. 验证命令。
8. 已识别风险。
9. 外部依赖或阻塞项。
10. 当前 Git 基线。

未完成上述输出前，不得开始修改。

### 三、实施边界

实施过程中必须遵守：

1. 仅进行满足当前任务验收标准所需的最小修改。
2. 禁止实施当前任务未要求的重构、升级、改名、格式化或目录迁移。
3. 禁止批量创建后续任务需要的空模块、空接口、空表或占位页面。
4. 禁止修改 `AGENTS.md`、`CLAUDE.md` 和共享契约，除非当前任务明确要求。
5. 保护用户未提交改动，不覆盖、不还原、不移动来源不明的用户文件。
6. 禁止执行：

   * `git commit`
   * `git push`
   * `git pull --rebase`
   * `git rebase`
   * `git reset --hard`
   * `git clean -fd`
   * `git checkout -- .`
   * `git restore .`
   * force push
7. 不得为了让测试通过而删除测试、跳过测试、降低断言、放宽权限、吞掉异常或伪造返回值。
8. 不得用 Mock 冒充真实外部系统联调结果。
9. 不得修改与当前任务无关的代码风格、换行符、依赖版本或锁文件。
10. 发现超出范围的问题时，只记录文件、位置、影响和建议任务编号。

### 四、数据库与状态更新规则

涉及数据库时必须遵守：

1. 数据库结构变化必须新增 Flyway 迁移。
2. 禁止直接修改已经发布或已经在其他环境执行过的迁移。
3. 迁移必须支持全新数据库按顺序执行。
4. 表、索引、唯一约束、外键或检查约束必须与并发和幂等要求相匹配。
5. 金额统一使用整数分，不得使用 `float` 或 `double`。
6. 金额、订单状态、支付状态、设备调用状态等关键字段必须使用条件更新或明确字段更新。
7. 禁止使用整实体更新覆盖金额、状态、租户、停车场或审计字段。
8. 涉及并发唯一性时，不得只依赖“先查询再插入”的应用层判断。
9. 所有重要状态迁移必须验证当前状态是否合法。
10. 数据库变更必须包含迁移验证、约束验证和回滚或恢复说明。

### 五、数据权限与安全边界

所有租户、停车场、设备、员工、车主、车辆、订单和图片数据必须由后端失败关闭。

必须遵守：

1. 不得信任客户端传入的 `tenantId`、`parkingLotId`、`deviceSn`、`userId` 或角色信息。
2. 后端必须从登录上下文、授权关系和可信业务记录中解析数据范围。
3. 列表、详情、创建、修改、删除、导出、统计和 WebSocket 推送都必须进行数据范围校验。
4. 无上下文、非法上下文、越权上下文和伪造上下文必须明确拒绝。
5. 禁止通过返回空数据掩盖本应拒绝的越权请求。
6. 异步消息、定时任务和 WebSocket 同样必须携带或重新建立可信上下文。
7. 前端隐藏菜单或按钮不能代替后端权限校验。
8. 日志不得输出密码、Token、密钥、完整手机号、支付证书或其他敏感信息。
9. 高风险操作必须记录操作人、目标对象、原因、前后值和执行结果。
10. 涉及跨租户、跨停车场或跨用户场景时，必须添加拒绝测试。

### 六、Device Access 专项规则

涉及 Device Access 时必须以当前共享契约为唯一接口事实来源。

当前规则：

1. v0.2 当前共有 7 个 HTTP 端点：

   * 设备 CRUD 5 个；
   * 设备校时 1 个；
   * 设备状态查询 1 个。
2. 当前 v0.2 没有 `gate/open`。
3. 开闸能力当前标记为 `INTENTIONALLY_OUT_OF_SCOPE_IN_V0.2`。
4. 不得创建、恢复或假设以下当前不存在的能力：

   * `openGate` HTTP Client；
   * `/gate/open` 接口调用；
   * 开闸 Mock 冒充正式契约；
   * 车牌识别事件；
   * 图片上传或补传；
   * HMAC；
   * 关闸；
   * 抓拍；
   * 重启；
   * 信路通真实接口。
5. 当前任务需要的能力不在共享契约中时，必须标记为“外部契约阻塞”，不得自行设计生产接口继续实施。
6. 业务层不得自行拼接 Device Access URL。
7. 浏览器、小程序和前端页面不得直接访问 Device Access。
8. Device Access Base URL 必须来自后端可信配置，不得由前端传入。
9. 状态快照必须标记采集时间，不得把缓存数据展示为实时数据。
10. 不得自行添加服务端尚未支持的认证头、参数或协议。

未来共享契约正式增加真实动作类接口后，动作调用还必须遵守：

* 调用前持久化审计；
* 禁止透明自动重试；
* 网络中断、连接重置或读取超时进入 `UNCERTAIN`；
* 不得直接判定设备一定执行或一定未执行；
* 再次调用必须由人工确认，并关联原调用记录。

### 七、支付专项规则

涉及支付时必须遵守：

1. 所有金额使用整数分。
2. 支付业务订单和支付单必须分别建模并建立幂等关系。
3. 前端不得决定实际支付金额、商户主体或订单归属。
4. 支付回调必须完成：

   * 微信签名验证；
   * `appid` 校验；
   * `mchid` 校验；
   * `outTradeNo` 校验；
   * 金额校验；
   * 订单归属校验；
   * 回调幂等校验；
   * 当前状态校验。
5. 支付成功不得直接绕过业务编排修改出场完成状态。
6. 补偿任务不得导致重复扣款、重复结算或重复设备动作。
7. 商户号、证书、APIv3 密钥和私钥不得明文写入代码、数据库普通字段、Git 或日志。
8. 没有真实微信资料时，只允许完成接口抽象和明确标记的 Mock 测试。
9. 未通过支付安全测试不得声明真实支付联调完成。
10. 真实凭证缺失属于外部依赖，不得用伪造生产参数代替。

### 八、Mock 与测试入口规则

1. Mock、人工事件和测试接口只能用于 `local` 或 `test` 环境。
2. `prod` 环境必须不存在、关闭或强制拒绝测试入口。
3. Mock 数据必须记录明确的来源标识。
4. 不得使用与未来正式 Device Access 事件相同的生产路由、Topic 或认证方式制造已联调假象。
5. 不得将 Mock 测试结果写成“真机联调通过”。
6. 不得将人工触发结果写成“自动识别闭环通过”。

### 九、验证要求

测试命令必须来自当前仓库真实的：

* `pom.xml`
* Maven Wrapper
* `package.json`
* 锁文件
* Docker Compose 文件
* 项目脚本
* 测试配置

不得凭经验虚构命令。

按照以下顺序验证：

1. 当前修改对应的最小单元测试。
2. 当前模块测试。
3. 受影响调用链的集成测试。
4. 必要的前端类型检查、构建或 E2E。
5. 必要的数据库迁移和约束测试。
6. 必要的接口、权限、并发和异常测试。
7. `git diff --check`。
8. 最终 `git status --short`。
9. 最终 `git diff --stat`。
10. 人工检查最终 diff 是否包含任务范围外修改。

根据任务性质，至少覆盖适用的场景：

* 正常路径；
* 参数非法；
* 重复请求；
* 幂等；
* 并发；
* 越权；
* 跨租户；
* 跨停车场；
* 跨用户；
* 状态非法；
* 外部服务超时；
* 事务回滚；
* 服务重启或消息重复。

无法运行的测试必须明确写出：

* 未运行的命令；
* 未运行原因；
* 需要的环境或外部资料；
* 对验收结论的影响。

禁止把“未运行”写成“通过”。

### 十、强制停止条件

出现以下情况时，停止受影响的代码实施并上报：

1. 当前任务前置依赖未完成。
2. 规范性文档、共享契约或关键源码缺失。
3. 任务卡与当前共享契约冲突。
4. 任务要求使用当前契约不存在的 Device Access 能力。
5. 用户未提交改动与本任务修改范围直接重叠，且无法安全合并。
6. 需要真实密钥、商户资料、域名、设备 SN、现场人员或真机环境，但用户尚未提供。
7. 必须修改已发布 Flyway 迁移才能继续。
8. 必须执行破坏性 Git 或数据库操作才能继续。
9. 需要改成微服务、更换数据库、替换主框架或进行大范围架构调整。
10. 继续实施只能依赖伪造接口、假数据或无法验证的假设。

停止时必须提供证据和最小可执行建议，不得通过临时假实现绕过阻塞。

### 十一、完成报告

完成后严格输出以下十项报告：

1. **任务结论**

   * `COMPLETED`、`PARTIALLY_COMPLETED` 或 `BLOCKED`
   * 是否达到当前任务验收标准

   * 按当前任务验收标准逐项说明
   * 不列入当前任务外的工作

3. **修改文件**

   * 新增、修改、删除文件分别列出
   * 说明每个文件的修改目的

4. **数据库变更**

5. **接口与契约变更**

   * 租户、停车场、设备、用户和角色范围
   * 幂等、并发、状态更新和日志脱敏结果

8. **未完成内容与阻塞项**

   * 未完成原因

- **停止条件**：任一上线前禁止项存在，结论必须是“不允许全面正式商用”。

## 6. 四周受控试运营排期建议

该排期是关键路径，不是完整第一阶段承诺。单人开发应以任务验收为准，不应为了赶周数跳过 P0 测试。

### 第 1 周：基线、工程和隔离

目标任务：T01–T16。

最低验收：
- 仓库事实基线明确；
- 后端和三个前端工程可构建；
- MySQL、Redis、RabbitMQ、WebSocket 和 Docker 本地环境可验证；
- 登录、固定角色、租户和停车场数据范围 fail-closed。

降级：
- 历史仓库迁移复杂时，先完成后端和 admin-web，booth-web/miniapp 只保留最小骨架；
- 不得降低多租户隔离标准。

### 第 2 周：停车场、设备台账和当前 Device Access 接口

目标任务：T18–T33。

最低验收：
- 一个停车场、一进一出、C5H 平台设备和可信 SN 映射可配置；
- **SUPERSEDED_BY_SHARED_CONTRACT**：旧 gate/open 前提已失效。v0.2 仅有校时和状态查询。开闸需待阶段 1 共享契约实施后验证；
- 开闸无自动重试，超时进入 UNCERTAIN；
- 使用测试事件创建入场和停车记录，岗亭可实时查看。

降级：
- 没有安全真机时，只运行 HTTP Mock；
- 没有识别事件契约时，只使用生产禁用的 Mock/人工触发。

### 第 3 周：计费、订单、车主端和放行编排

目标任务：T34–T41、T47。

最低验收：
- 一个真实测试收费规则可正确计费；
- 停车订单和零元结清稳定；
- 小程序可绑定车牌、查看当前停车和费用；
- 出口测试事件可触发放行判断、开闸和出场完成；
- 未支付车辆不能自动放行。

有真实收费要求时，追加 T42–T46；无微信资料时不得向真实车主收费。

### 第 4 周：岗亭兜底、部署和连续运行

目标任务：T48–T52。

最低验收：
- 人工放行、车牌修正、UNCERTAIN 处置可用；
- 部署、备份恢复和故障演练通过；
- 单停车场测试车辆连续运行；
- 每一笔通行、订单、支付/零元、设备调用和出场可追溯。

若 Device Access 未提供正式识别事件，最终结论只能是“平台业务链路与开闸接口受控联调通过”，不能写“真机自动入场完整闭环通过”。

## 7. 单人开发工期参考

|---|---:|---:|---|

| M2 账号与租户 | 6–10 日 | 3–5 日 | 多租户测试不可压缩 |
| M3 停车场配置 | 5–8 日 | 2–4 日 | 取决于现有后台复用 |

| M7 车主与支付 | 12–20 日 | 6–10 日 | 双商户和微信资料风险高 |

## 9. 每个任务完成后的复核问题

1. 是否只完成本任务，没有顺手扩展？
2. 是否保护了用户未提交改动？
3. 是否存在跨租户、跨停车场、跨用户或设备越权？
4. 是否直接信任了前端 tenantId、parkingLotId 或 deviceSn？
5. 是否修改了已发布 Flyway 迁移？
6. 是否用整实体更新金额或状态？
7. 是否出现开闸自动重试或把超时当作未动作？
8. 是否把目标 Device Access 能力写成当前可用？
9. 是否完整验证正常、重复、并发、越权和异常路径？
10. 是否输出了真实 Git 状态和未运行测试？
